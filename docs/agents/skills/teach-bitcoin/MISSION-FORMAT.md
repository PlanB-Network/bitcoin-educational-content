# MISSION.md format

`MISSION.md` lives at the workspace root. It captures *why* the learner is
pursuing this topic. Every teaching decision — what to teach next, which
resources to surface, which **door** to recommend — traces back to this file.

## Template

```md
# Mission: {Topic}

## Why
{1-3 sentences. The concrete real-world outcome. What changes in their life or
work once they have this skill? Push past "to understand X" to the underlying
goal.}

## Success looks like
- {A specific, observable thing the learner will be able to do}
- {Another specific thing}

## Right door (Plan ₿ Academy)
- Starting point: {course id — name, level}  (e.g. btc101 — The Bitcoin Journey, beginner)
- Next: {course/tutorial id — name}
- Updated: {YYYY-MM-DD}

## Constraints
- {Time, budget, hardware, prior commitments, learning preferences}

## Out of scope
- {Adjacent topics explicitly deferred — protects the zone of proximal development}
```

## Rules

- **One mission per workspace.** Two unrelated goals = two workspaces.
- **Concrete over abstract.** "Self-custody my savings on my own node by
  September" beats "understand Bitcoin." "Accept bitcoin in my café" beats "learn
  Lightning."
- **Push back on vagueness.** If the learner cannot say why, interview them
  before writing anything. A bad mission is worse than none.
- **Keep the right door current.** When the learner's level changes, update the
  recommended door (and write a learning record).
- **Revise when reality shifts**, and **keep it short** — past one screen it has
  stopped being a compass and become a plan.
