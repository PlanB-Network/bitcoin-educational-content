# เจาะลึก Simplicity

การเจาะลึกทฤษฎีและการตัดสินใจด้านการออกแบบเบื้องหลังภาษา Simplicity โดยอิงจากชุดบทความ ["Delving Simplicity"](https://delvingbitcoin.org/t/delving-simplicity-part-three-fundamental-ways-of-combining-computations/1902) ครบทั้งห้าตอนของ [Dr. Russell O'Connor](https://r6.ca/) ผู้สร้าง Simplicity ที่ Blockstream Research หลักสูตรนี้อธิบายว่า *ทำไม* Simplicity จึงถูกออกแบบมาเช่นนี้ ไม่ใช่วิธีเขียนมัน

หลักสูตรนี้เดินตามบทความของ Dr. O'Connor ผ่านวิธีพื้นฐานสามแบบในการรวมการคำนวณ ระบบชนิดข้อมูลขั้นต่ำและทฤษฎีบทความสมบูรณ์ของมัน การสร้างชนิดข้อมูลและเลขคณิตที่ใช้งานได้จริงจากหลักการพื้นฐาน การแนะนำ side effects อย่างระมัดระวังเพื่อการโต้ตอบกับบล็อกเชน และสุดท้ายว่าโปรแกรมถูกผูกมัดเข้ากับที่อยู่และถูกใช้จ่ายคืนบนเชนอย่างไร

### สิ่งที่คุณจะได้เรียนรู้

หลักสูตรนี้สำรวจปรัชญาการออกแบบและรากฐานทางคณิตศาสตร์เบื้องหลัง Simplicity ภาษา scripting รุ่นถัดไปที่เปิดใช้งานบน [Liquid Network](https://blockstream.com/press-releases/2025-07-31-blockstream-launches-simplicity/) ในเดือนกรกฎาคม 2025 หลักสูตรนี้ติดตามชุดบทความครบทั้งห้าตอนและจัดโครงสร้างเป็นสองส่วนเนื้อหาหลัก:

1. **รากฐานของ Simplicity** — ทำไมการคำนวณบนบล็อกเชนจึงต้องการภาษาที่แตกต่างในระดับพื้นฐาน วิธีสามแบบในการรวมปฏิบัติการ (ตามลำดับ, ขนาน, มีเงื่อนไข) และ combinator แกนหลักทั้งเก้าตัวที่ก่อรูปเป็นภาษาที่สมบูรณ์ทางคณิตศาสตร์
2. **จากชนิดข้อมูลสู่โปรแกรม** — การสร้างตรรกะบูลีน เลขคณิต และ SHA-256 จากหลักการพื้นฐาน การเข้าใจ side effects แบบ Failure และ Reader ที่ทำให้เกิดการโต้ตอบกับบล็อกเชน และการเรียนรู้ว่าโปรแกรมถูกผูกมัดเข้ากับที่อยู่ Taproot ผ่าน Commitment Merkle Roots และถูกใช้จ่ายคืนด้วยข้อมูล witness อย่างไร

- ความคุ้นเคยกับสัญกรณ์ทางคณิตศาสตร์บ้างจะช่วยได้ แต่ไม่จำเป็น เราจะแนะนำทุกอย่างไปตามลำดับ

## Simplicity คืออะไร?

<chapterId>d04f3960-d7fb-44e1-b5a3-25b33d03fd38</chapterId>

หากคุณเข้ามาเรียนหลักสูตรนี้โดยไม่มีพื้นฐานเกี่ยวกับ Simplicity บทนี้จะช่วยให้คุณตั้งหลักก่อนที่เราจะดำดิ่งสู่ส่วนลึก

### Simplicity แบบสรุปสั้น

Simplicity คือ **ภาษา smart contract แบบ Bitcoin-native** ที่ใช้งานจริงบน Liquid Network แล้วในปัจจุบัน Dr. Russell O'Connor จินตนาการถึงมันครั้งแรกประมาณปี 2012 และอธิบายรายละเอียดในงานวิจัยปี 2017 ของเขา *Simplicity: A New Language for Blockchains* มันถูกเปิดใช้งานบน Liquid Network ในเดือนกรกฎาคม 2025 หลังจากหลายปีของการ formal verification และการพัฒนา

ต่างจาก Solidity ของ Ethereum ซึ่งเป็นภาษา contract ระดับสูงแบบ Turing-complete, Simplicity ตั้งใจให้มีความเรียบง่ายขั้นต่ำ มันมี:
- **ตัวสร้างชนิดข้อมูลสามแบบ** (unit, sum, product)
- **combinator เก้าตัว** (ปฏิบัติการพื้นฐานและกฎการประกอบ)
- **ไม่มี loop, ไม่มี recursion, ไม่มีหน่วยความจำแบบ dynamic**

จาก primitive เพียงเท่านี้ คุณสามารถสร้างการคำนวณใด ๆ ที่จำเป็นสำหรับการตรวจสอบธุรกรรมได้ ตั้งแต่ตรรกะบูลีนไปจนถึงการแฮช SHA-256 เต็มรูปแบบ

### วันนี้คุณทำอะไรกับ Simplicity ได้บ้าง?

Simplicity กำลังขับเคลื่อนแอปพลิเคชันจริงบน Liquid Network แล้ว ตัวอย่างที่โดดเด่นที่สุดคือ [Simplicity DEX](https://docs.simplicity-lang.org/use-cases/simplicity-dex/) ตลาดออปชันแบบไม่ใช้ oracle ที่ผู้ใช้ซื้อขาย call options บน L-BTC โดยใช้ USDt เป็นหลักประกัน (contract พื้นฐานยังรองรับ puts ด้วย) โครงการ Simplicity ที่ใช้งานจริงอื่น ๆ ได้แก่ [Swaption](https://swaption.io/) โดย SideSwap (ออปชัน) และ [Deadcat](https://github.com/Resolvr-io/deadcat) แบบโอเพนซอร์สโดย Resolvr (ตลาดทำนายผล) นอกเหนือจาก DeFi แล้ว Simplicity ยังเปิดทางให้เงื่อนไขการใช้จ่ายขั้นสูง เช่น vaults, covenants และรูปแบบ multisig ซับซ้อนที่เป็นไปไม่ได้หรือไม่ปลอดภัยใน Bitcoin Script

### หลักสูตรนี้คืออะไร — และไม่ใช่อะไร

นี่ **ไม่ใช่** บทเรียนเขียนโค้ดแบบลงมือทำ คุณจะไม่ได้เขียนโปรแกรม Simplicity ที่นี่ หากคุณกำลังมองหาสิ่งนั้น ลองดู:
- [simplicity-lang.org](https://simplicity-lang.org/) — เอกสารทางการและภาษา high-level SimplicityHL
- [คลัง Simplicity GitHub](https://github.com/BlockstreamResearch/simplicity) — reference implementation, ตัวอย่าง และ Rocq proofs
- [โพสต์บล็อก Blockstream](https://blog.blockstream.com/en-simplicity-github/) เกี่ยวกับการเริ่มต้นใช้งาน

สิ่งที่หลักสูตรนี้ **มุ่งเน้น** คือ **ทางเลือกเชิงปรัชญาและเชิงเทคนิค** เบื้องหลังการออกแบบของ Simplicity ทำไมภาษานี้จึงถูกสร้างขึ้นในลักษณะนี้? ทำไมมี combinator เพียงเก้าตัว? ทำไมไม่มี recursion? ทำไมการที่ระบบชนิดข้อมูลเชื่อมโยงกับ sequent calculus ของ Gentzen จึงสำคัญ?

ให้คิดว่านี่คือการเข้าใจ **ทำไมเครื่องยนต์จึงถูกสร้างมาแบบนี้** มากกว่าการเรียนขับรถ

### เหมาะสำหรับใคร?

หลักสูตรนี้เหมาะสำหรับ:
- **นักพัฒนาโปรโตคอล** ที่ต้องการเข้าใจรากฐานของ Simplicity ก่อนเขียนโค้ด
- **นักวิจัย Bitcoin** ที่สนใจ formal verification และแนวทางตามทฤษฎีชนิดข้อมูล
- **นักวิทยาการคอมพิวเตอร์** ที่สนใจความเชื่อมโยงระหว่าง sequent calculus กับการคำนวณบนบล็อกเชน
- **bitcoiner ขั้นสูง** ที่ต้องการไปไกลกว่าความเข้าใจผิวเผินเกี่ยวกับความสามารถด้าน scripting ของ Liquid

หากคำอย่าง "sum types", "combinators" หรือ "sequent calculus" เป็นเรื่องใหม่ทั้งหมดสำหรับคุณ ไม่ต้องกังวล เราจะอธิบายทุกอย่างตั้งแต่ต้น แต่เตรียมตัวสำหรับการเดินทางที่หนาแน่นและเป็นคณิตศาสตร์

### จากบทความสู่หลักสูตร

ชุดบทความ "Delving Simplicity" ต้นฉบับโดย Dr. O'Connor มีโครงสร้างเป็นบทความเทคนิคห้าตอน หลักสูตรนี้จัดระเบียบและใส่คำอธิบายประกอบเนื้อหานั้นใหม่ให้เป็นเส้นทางการเรียนรู้แบบก้าวหน้า พร้อมแบบทดสอบเพื่อทดสอบความเข้าใจของคุณระหว่างทาง แนวคิด นิยาม และพิสูจน์เป็นของเขา และเราได้ปรับรูปแบบเพื่อการศึกษาที่มีโครงสร้าง

# รากฐานของ Simplicity

<partId>a5976618-94ab-4b29-b9aa-040d35c68e5d</partId>

## วิธีพื้นฐานในการรวมการคำนวณ

<chapterId>6d46e77a-7e60-473b-b230-418da5ae44eb</chapterId>

ตอนนี้ Simplicity ได้ถูกเปิดใช้งานบน Liquid Network แล้ว ผมอยากเจาะลึกปรัชญาและการออกแบบของภาษา Simplicity อย่างละเอียด

การตรวจสอบธุรกรรมของ Bitcoin เป็นแอปพลิเคชันที่แตกต่างอย่างมากจากการออกแบบภาษาโปรแกรมทั่วไป ต้นทุนพื้นที่บล็อกมีราคาสูง ดังนั้นโปรแกรมจึงต้องกะทัดรัด โปรแกรมในธุรกรรม Bitcoin จะถูกเรียกใช้กับอินพุตเดียวเท่านั้น และทุกคนเรียกใช้โปรแกรมกับอินพุตเดียวกัน นอกจากนี้ ตัวแทนที่อนุมัติธุรกรรมรู้อยู่แล้วล่วงหน้าว่าผลลัพธ์ของการคำนวณคืออะไร: ธุรกรรมนั้นถูกต้อง

โดยทั่วไป ตัวแทนที่อนุมัติจะเรียกใช้การคำนวณที่แพงกว่ามากเพื่อสร้างข้อมูล witness ที่รับรองความถูกต้องของธุรกรรม ในขณะที่โปรแกรมที่ทำงานบนบล็อกเชนต้องตรวจสอบความถูกต้องของข้อมูล witness การตรวจสอบความถูกต้องมักถูกกว่าการพิสูจน์ความถูกต้องมาก

เราออกแบบ Simplicity โดยคำนึงถึงความท้าทายเฉพาะเหล่านี้ในการออกแบบภาษา ตัวอย่างเช่น Simplicity กำหนดให้ branch ที่ไม่ได้ถูกเรียกใช้ต้องถูก prune เพื่อไม่ให้ปรากฏบนบล็อกเชน ขั้นตอน preprocessing ถูกออกแบบอย่างระมัดระวังให้มี time complexity แบบ (กึ่ง)เชิงเส้นตามขนาดของโปรแกรม Simplicity ใช้ static analysis แทน "gas" ซึ่งไม่สามารถคำนวณได้โดยไม่เรียกใช้โค้ดในลักษณะที่กำหนดไว้ เพื่อไม่ให้รายละเอียดของ execution model กลายเป็นเรื่อง consensus critical ไม่มีการจัดสรรหน่วยความจำแบบ dynamic ระหว่างการทำงาน และอื่น ๆ

ก่อนจะเจาะลึกรายละเอียดการออกแบบของ Simplicity ผมต้องการเริ่มชุดบทความนี้ด้วยปรัชญาการเขียนโปรแกรมเกี่ยวกับวิธีทั่วไปในการรวม building blocks พื้นฐานเพื่อสร้าง functionality ใหม่

### การประกอบ

สมมติว่าคนหนึ่งกำลังออกแบบภาษาสำหรับธุรกรรมที่โปรแกรมได้สำหรับบล็อกเชนอย่าง Bitcoin โดยเฉพาะ โปรแกรมเข้าถึงได้เฉพาะข้อมูลธุรกรรมและข้อมูล UTXO ของอินพุต และการทำงานใช้เพียงตัดสินความถูกต้องของธุรกรรม (ซึ่งทำให้ cache ผลลัพธ์ของการทำงานได้) สมมติว่าเริ่มจากชุดปฏิบัติการพื้นฐานบางชุดที่ทำงานต่าง ๆ ได้ เช่น การคำนวณพื้นฐาน การอ่านและ/หรือประมวลผลข้อมูลจากธุรกรรม และการตรวจสอบลายเซ็น แต่ละปฏิบัติการบริโภคอินพุตบางชนิด (อาจว่างเปล่า) และคืนเอาต์พุตบางชนิด เราสามารถรวมปฏิบัติการพื้นฐานเหล่านี้ให้เป็นปฏิบัติการที่ซับซ้อนขึ้นได้ด้วยวิธีใดบ้าง?

### การประกอบแบบตามลำดับ

![การประกอบแบบตามลำดับ](assets/en/001.webp)

วิธีการประกอบที่พื้นฐานที่สุดคือการประกอบแบบตามลำดับ หากเรามีปฏิบัติการพื้นฐานสองตัว โดยที่ชนิดข้อมูลเอาต์พุตของตัวหนึ่งตรงกับชนิดข้อมูลอินพุตของอีกตัวหนึ่ง เราก็สามารถรวมปฏิบัติการทั้งสองเป็นปฏิบัติการประกอบใหม่ได้ ปฏิบัติการใหม่นี้เรียกใช้ปฏิบัติการพื้นฐานทั้งสองตามลำดับ โดยรับอินพุตของปฏิบัติการแรกเป็นอินพุต ส่งเอาต์พุตของปฏิบัติการแรกนั้นเข้าเป็นอินพุตของปฏิบัติการที่สอง และท้ายที่สุดคืนเอาต์พุตของปฏิบัติการที่สองนั้น

แน่นอน เราไม่จำเป็นต้องจำกัดตัวเองอยู่แค่การรวมปฏิบัติการพื้นฐาน ตอนนี้เรามีปฏิบัติการประกอบบางตัวแล้ว เราก็สามารถรวมปฏิบัติการเหล่านั้นด้วย functional composition ได้เช่นกัน

ในคณิตศาสตร์ การประกอบแบบตามลำดับนี้มักถูกเรียกเพียงว่า "composition" และอาจทำให้คิดว่านี่เป็นวิธีเดียวในการประกอบสิ่งต่าง ๆ อย่างไรก็ตาม เรายังมีวิธีอื่นในการประกอบปฏิบัติการ

### การประกอบแบบขนาน

![การประกอบแบบขนาน](assets/en/002.webp)

สมมติว่าเรามีปฏิบัติการสองตัว ซึ่งอาจเป็นปฏิบัติการพื้นฐานหรือซับซ้อนก็ได้ และทั้งสองรับอินพุตชนิดเดียวกัน วิธีพื้นฐานที่สองในการประกอบปฏิบัติการทั้งสองนี้คือการเรียกใช้ทั้งคู่บนอินพุตเดียวกัน สิ่งนี้เรียกว่าการประกอบแบบขนาน และชนิดของเอาต์พุตคือ "product" ของชนิดเอาต์พุตของปฏิบัติการเดิม และประกอบด้วยคู่ของเอาต์พุตทั้งสอง

แม้สิ่งนี้จะถูกเรียกว่า composition แบบ "ขนาน" และโดยหลักการแล้วปฏิบัติการทั้งสองอาจถูกเรียกใช้แบบขนานได้ แต่การทำงานแบบขนานไม่ใช่ข้อกำหนดเชิงปฏิบัติการ เราสามารถ implement การประกอบแบบขนาน "ตามลำดับ" โดยเรียกใช้ปฏิบัติการหนึ่งก่อนแล้วตามด้วยอีกปฏิบัติการหนึ่ง เราไม่สนใจรายละเอียดว่าการประกอบแบบขนานถูก implement อย่างไร ตราบใดที่เอาต์พุตเหมือนเดิม

### การประกอบแบบมีเงื่อนไข

![การประกอบแบบมีเงื่อนไข](assets/en/003.webp)

การประกอบแบบมีเงื่อนไขเป็น dual ของการประกอบแบบขนาน ในกรณีนี้เรามีปฏิบัติการสองตัวที่สร้างเอาต์พุตเดียวกัน และเราประกอบมันโดยเลือกตัวหนึ่งให้ทำงาน อินพุตของปฏิบัติการประกอบนี้คือ "sum" หรือ "tagged union" ของชนิดอินพุตของปฏิบัติการเดิม ในตัวอย่างนี้ tag, "Left" หรือ "Right" เป็นบิตเดียวในข้อมูลอินพุตที่กำหนดว่ากำลังถือข้อมูลชนิดใดอยู่ และดังนั้นปฏิบัติการใดในสองตัวจึงสามารถถูกเรียกใช้ได้

การประกอบแบบมีเงื่อนไขทำงานในลักษณะเดียวกันแม้อินพุตจะเป็น sum ของชนิดข้อมูลที่เหมือนกันสองชนิด sum type ยังคงมี tag และค่าของ tag นั้นกำหนดว่าปฏิบัติการใดในสองตัวจะถูกเรียกใช้

### การประกอบใน Bitcoin Script

มีหลายวิธีในการทำให้การประกอบสามชนิดนี้เกิดขึ้นในภาษาโปรแกรมต่าง ๆ ใน Bitcoin Script การประกอบแบบตามลำดับเกิดขึ้น (โดยประมาณ) ผ่านการต่อ routine สองตัวเข้าด้วยกัน (นี่คือเหตุผลที่ Bitcoin Script ถูกเรียกว่า concatenative programming language) เพราะเอาต์พุตของ routine หนึ่งถูกทิ้งไว้บน stack ให้ routine ถัดไปบริโภค การประกอบแบบขนานทำได้โดยใช้ปฏิบัติการ duplicate และ swap เพื่อจัดการ stack ให้ routine สองตัวสามารถทำงานบนอินพุตเดียวกันได้ เรื่องนี้ไม่ตรงไปตรงมาทั้งหมด เพราะสิ่งที่เราเรียกว่า "product" ของชนิดข้อมูลโดยทั่วไปมักเกิดขึ้นผ่านการใช้ stack item หลายตัว หวังว่าคุณจะเห็นแนวคิดทั่วไป

แน่นอนว่าการประกอบแบบมีเงื่อนไขทำได้โดย `OP_IF` ซึ่ง branch ตามค่าบน stack ในกรณีนี้ stack item ด้านบนทำหน้าที่เป็น tag และโดยปกติ item ถัดไปหรือหลาย item ถัดไปบน stack เป็น "ชนิด" ที่ต่างกันซึ่งขึ้นกับค่าของ tag สำหรับแต่ละกรณี ชนิดของ stack item อาจเหมาะสำหรับการประมวลผลโดย branch หนึ่งของ `OP_IF` เท่านั้น อย่างไรก็ตามหลังจากเราถึง `OP_ENDIF` แล้ว stack item ต้องมี "ชนิด" ที่สอดคล้องกัน เพื่อให้ script ที่เหลือสามารถดำเนินต่อได้โดยไม่ขึ้นกับว่า branch ใดถูกเลือกก่อนหน้า

### การประกอบใน Simplicity

เราออกแบบ Simplicity ด้วย combinator ที่ implement การประกอบสามรูปแบบนี้โดยตรง เมื่อรวมกับ combinator อีกไม่กี่ตัวเพื่อรองรับปฏิบัติการพื้นฐานอื่นที่เกี่ยวข้องกับ product type และ sum type ภาษา Simplicity แกนหลักจึงประกอบด้วย combinator เก้าตัวซึ่งเพียงพอสำหรับแสดงการคำนวณจำกัดใด ๆ เราจะพูดเรื่องนี้ละเอียดขึ้นในบทถัดไป

### การประกอบชนิดที่สี่

ก่อนจบ เราควรกล่าวว่ายังมีการประกอบอีกอย่างน้อยหนึ่งชนิดที่พบในวิทยาการคอมพิวเตอร์ นั่นคือ "recursive composition" ใน recursive composition ปฏิบัติการหนึ่งถูกทำซ้ำหลายครั้ง

โปรดสังเกตว่า Bitcoin Script ไม่รองรับ recursive composition และเช่นเดียวกัน เราได้ตัด unbounded recursion ออกจากการออกแบบของ Simplicity อย่างชัดเจน วิทยานิพนธ์ของเราคือการคำนวณแบบวนซ้ำไม่จำกัดเหมาะกว่าที่จะ implement ด้วย recursive covenants ซึ่งคำนวณข้ามหลายธุรกรรม สิ่งนี้ช่วยให้ผู้ใช้หลีกเลี่ยงข้อจำกัดด้านพื้นที่บล็อกและ standardness และคาดการณ์ต้นทุนธุรกรรมได้ดีขึ้น

อย่างไรก็ตาม มีวิธี abuse ฟีเจอร์ delegation ของ Simplicity เพื่อให้ได้สิ่งที่คล้ายกับ unbounded recursive composition ซึ่งเราอาจพูดถึงภายหลังในชุดบทความนี้

### สรุป

เราได้ทบทวนรูปแบบหลักสามแบบของการประกอบสำหรับแปลงปฏิบัติการพื้นฐานให้เป็นปฏิบัติการซับซ้อน:

- การประกอบแบบตามลำดับ
- การประกอบแบบขนาน
- การประกอบแบบมีเงื่อนไข

เราได้พูดถึงว่ารูปแบบการประกอบเหล่านี้เกิดขึ้นใน Bitcoin Script อย่างไร และเกริ่นว่ามันมีอิทธิพลต่อการออกแบบภาษา Simplicity อย่างไร เราสังเกตว่าการประกอบชนิดที่สี่ คือ recursive composition ถูกตัดออกโดยเฉพาะจากทั้ง Simplicity และ Bitcoin Script

ในบทถัดไป เราจะอธิบาย combinator ทั้งเก้าตัวที่ประกอบเป็นแกนของภาษา Simplicity ว่ามันช่วยให้เกิดการประกอบสามรูปแบบนี้โดยตรงได้อย่างไร และสิ่งนี้ก่อรูปเป็นภาษาที่สมบูรณ์สำหรับอธิบายการคำนวณจำกัดใด ๆ ได้อย่างไร

## ความสมบูรณ์ของ combinator ใน Simplicity

<chapterId>2a10a6ba-fada-4556-a673-3ae8c0794bf0</chapterId>

ในบทนี้ เราจะแนะนำภาษา Simplicity แกนหลักและแสดงว่าภาษานี้สมบูรณ์ หมายความว่าการคำนวณจำกัดใด ๆ สามารถแสดงภายในมันได้

### ชนิดข้อมูลของ Simplicity

Simplicity รองรับ type constructor พื้นฐานสามแบบ product type `A × B` แทนเอาต์พุตของการประกอบแบบขนาน ส่วน sum type `A + B` (tagged union) จัดการอินพุตของการประกอบแบบมีเงื่อนไข ชนิดที่สามคือ unit type

### Unit Type

unit type ซึ่งเขียนเป็น `𝟙` หรือ `ONE` มีค่าอยู่หนึ่งค่าเท่านั้น: empty tuple `⟨⟩` หรือ `()` ชนิดข้อมูลศูนย์บิตนี้ไม่บรรทุกข้อมูลใด ๆ

### Sum Type

sum type `A + B` รวมสองชนิดเข้าด้วยกันพร้อม tag ที่บอกว่า "left" หรือ "right" ค่าเขียนเป็น `σᴸ(a)` หรือ `inl(a)` สำหรับค่าที่ติด tag ซ้าย และ `σᴿ(b)` หรือ `inr(b)` สำหรับค่าที่ติด tag ขวา tag ยังคงแยกจากกันแม้จะรวมชนิดที่เหมือนกัน

#### Boolean Type

ชนิด `𝟙 + 𝟙` ซึ่งเขียนเป็น `𝟚` หรือ `TWO` แทนชนิดข้อมูลหนึ่งบิตที่มีสองค่า ตาม convention, `σᴸ⟨⟩` แทน false/zero ในขณะที่ `σᴿ⟨⟩` แทน true/one

### Product Type

product type `A × B` มีคู่ของค่าซึ่งเขียนเป็น `⟨a, b⟩` หรือ `(a, b)` ชนิด `𝟚 × 𝟚` มีสี่ค่า ซึ่งต่างจากสี่ค่าใน `𝟚 + 𝟚`

### นิพจน์แกนหลักของ Simplicity

ปฏิบัติการเขียนเป็น `f : A ⊢ B` หมายถึงชนิดอินพุต `A` และชนิดเอาต์พุต `B` Simplicity เป็น "first-order" — มันไม่มี function types

### ปฏิบัติการพื้นฐานสองตัว

ภาษาแกนหลักให้ปฏิบัติการพื้นฐานสองตัว:

**Identity (`iden`).** ปฏิบัติการ identity ส่งอินพุตผ่านไปโดยไม่เปลี่ยนแปลง:

```
iden : A ⊢ A
⟦iden⟧(a) = a
```

**Unit (`unit`).** ปฏิบัติการ unit ทิ้งอินพุตและคืน empty tuple:

```
unit : A ⊢ 𝟙
⟦unit⟧(a) = ⟨⟩
```

สิ่งเหล่านี้ก่อรูปเป็น family โดยมีหนึ่งปฏิบัติการต่อหนึ่งชนิดข้อมูล

### Combinator การประกอบสามตัว

การประกอบแบบตามลำดับใช้ `comp f g` (เขียนเป็น `f ⨾ g` หรือ `f >>> g`):

```
If f : A ⊢ B and g : B ⊢ C, then
comp f g : A ⊢ C
⟦f ⨾ g⟧(a) = ⟦g⟧(⟦f⟧(a))
```

การประกอบแบบขนานใช้ `pair f g` (เขียนเป็น `f ▵ g` หรือ `f &&& g`):

```
If f : A ⊢ B and g : A ⊢ C, then
pair f g : A ⊢ B × C
⟦f ▵ g⟧(a) = ⟨⟦f⟧(a), ⟦g⟧(a)⟩
```

การประกอบแบบมีเงื่อนไขใช้ `case f g : (A + B) × C ⊢ D` โดยให้ branch เข้าถึง environment ร่วม `C`:

```
If f : A × C ⊢ D and g : B × C ⊢ D, then
case f g : (A + B) × C ⊢ D
⟦case f g⟧⟨σᴸ(a), c⟩ = ⟦f⟧⟨a, c⟩
⟦case f g⟧⟨σᴿ(b), c⟩ = ⟦g⟧⟨b, c⟩
```

ทำไมการประกอบแบบมีเงื่อนไขจึงมีรูปแบบนี้ — sum ที่จับคู่กับ environment ร่วม `C` — แทนที่จะเป็น `copair f g : A + B ⊢ C` ที่เรียบง่ายกว่าและแค่เลือก branch? เพราะ `copair` เปล่า ๆ ไม่สามารถแสดง **distribution** ได้: ฟังก์ชัน `dist : (A + B) × C ⊢ A × C + B × C` ที่ผลักอินพุตร่วมเข้าไปใน branch ใดก็ตามที่ถูกเลือก ด้วยการใส่ environment `C` เข้าไปใน `case` โดยตรง Simplicity จึงได้ทั้งการประกอบแบบมีเงื่อนไข *และ* distribution จาก combinator ตัวเดียว — หนึ่งในการตัดสินใจออกแบบสำคัญที่ทำให้ภาษาแกนหลักเหลือ combinator เพียงเก้าตัว

### Combinator อีกสี่ตัว

การบริโภค product ใช้ `take` และ `drop`:

**take** ดึงองค์ประกอบด้านซ้าย:

```
If f : A ⊢ C, then
take f : A × B ⊢ C
⟦take f⟧⟨a, b⟩ = ⟦f⟧(a)
```

**drop** ดึงองค์ประกอบด้านขวา:

```
If f : B ⊢ C, then
drop f : A × B ⊢ C
⟦drop f⟧⟨a, b⟩ = ⟦f⟧(b)
```

การสร้าง sum ใช้ `injl` และ `injr`:

**injl** ห่อด้วย tag ซ้าย:

```
If f : A ⊢ B, then
injl f : A ⊢ B + C
⟦injl f⟧(a) = σᴸ(⟦f⟧(a))
```

**injr** ห่อด้วย tag ขวา:

```
If f : A ⊢ C, then
injr f : A ⊢ B + C
⟦injr f⟧(a) = σᴿ(⟦f⟧(a))
```

### Combinator แกนหลักทั้งเก้าตัว

โดยรวมแล้ว Simplicity มี combinator แกนหลักพอดีเก้าตัว:

| Combinator | วัตถุประสงค์ |
|---|---|
| `iden` | ส่งอินพุตผ่านไป |
| `unit` | ทิ้งอินพุต |
| `comp` | การประกอบแบบตามลำดับ |
| `pair` | การประกอบแบบขนาน |
| `case` | การประกอบแบบมีเงื่อนไข |
| `take` | ดึงค่าซ้ายจาก product |
| `drop` | ดึงค่าขวาจาก product |
| `injl` | inject เข้าไปด้านซ้ายของ sum |
| `injr` | inject เข้าไปด้านขวาของ sum |

### Simplicity และ Sequent Calculus

การออกแบบของ Simplicity มาจากส่วน conjunctive-disjunctive ของ sequent calculus ของ Gentzen กล่าวให้แม่นยำกว่านั้น มันเป็น variant ของ *functional interpretation* ของ sequent calculus ซึ่งเองก็คล้ายกับ Curry-Howard correspondence ระหว่าง natural deduction กับ lambda calculus กฎของ combinator แสดง "ชนิดที่เล็กกว่าใน premise มากกว่า conclusion" ทำให้ Bit Machine — interpreter เครื่อง stack เชิงนามธรรมของ Simplicity — ลดการคัดลอกข้อมูลระหว่างการทำงานได้

### ค่าไม่ใช่นิพจน์

นิพจน์ Simplicity หมายถึงปฏิบัติการ ไม่ใช่ค่า สัญกรณ์ `scribe b : A ⊢ B` แทนนิพจน์เฉพาะตัวที่คืนค่า `b` เสมอ โดยทำหน้าที่เป็นความสะดวกเชิงสัญกรณ์มากกว่าเป็น combinator สิ่งนี้สะท้อน Bitcoin Script ซึ่งปฏิบัติการอย่าง `OP_1` push ค่าแทนที่จะแสดงค่าตรง ๆ

### ทฤษฎีบทความสมบูรณ์ของ Simplicity

เมื่อมี combinator ทั้งเก้าตัวครบแล้ว เราจะรู้ได้อย่างไรว่าเราไม่ได้ขาดอะไร — ว่าทั้งเก้าตัวนี้พอจริง ๆ? ทฤษฎีบทความสมบูรณ์ของ Simplicity ตอบเรื่องนี้: สำหรับฟังก์ชันใด ๆ ระหว่างชนิด Simplicity (จำกัด) จะมีนิพจน์ Simplicity บางนิพจน์ที่หมายถึงมัน พิสูจน์นี้เป็น constructive — มันแสดงวิธีสร้างนิพจน์:

1. **แยกอินพุต**: ใช้นิพจน์ `case` แบบซ้อนกันเพื่อแยกอินพุตใด ๆ ของชนิดใด ๆ ออกเป็นบิตองค์ประกอบอย่างสมบูรณ์
2. **สร้าง lookup table**: สำหรับทุกอินพุตที่เป็นไปได้ ใช้ `scribe` เพื่อสร้างเอาต์พุตที่สอดคล้องกัน
3. **ประกอบเข้าด้วยกัน**: cases และ scribes ที่ซ้อนกันรวมกันเป็น lookup table ขนาดยักษ์ที่ implement ฟังก์ชันนั้น

ทฤษฎีบทนี้ได้รับการ formal verification ใน proof assistant Rocq (เดิมคือ Coq) พิสูจน์นี้เป็นส่วนหนึ่งของคลัง Simplicity ทางการและถูกตรวจสอบความถูกต้องด้วยเครื่องแล้ว

แม้ทฤษฎีบทความสมบูรณ์จะรับประกันว่า combinator เก้าตัวของ Simplicity สามารถแสดงฟังก์ชันใด ๆ ระหว่างชนิด Simplicity (จำกัด) ได้ แต่นิพจน์ที่ได้จากการสร้าง lookup table มีขนาดใหญ่จนใช้งานจริงไม่ได้ ฟังก์ชันบนอินพุต 256 บิตจะต้องใช้ lookup table ที่มีรายการ 2²⁵⁶ รายการ นี่คือเหตุผลที่บทถัดไปมุ่งเน้นการสร้างนิพจน์ที่มีประสิทธิภาพซึ่งใช้ประโยชน์จากโครงสร้างของการคำนวณ แทนที่จะ brute-force ทุกอย่างผ่าน lookup table

### สรุป

ภาษาแกนหลักของ Simplicity รวมระบบชนิดข้อมูลและ combinator ที่ทำให้การคำนวณจำกัดใด ๆ เป็นไปได้ แม้ทฤษฎีบทความสมบูรณ์จะรับประกันความสามารถในการแสดงออก แต่นิพจน์ที่ได้จากการสร้างแบบทั่วไปมีขนาดใหญ่จนใช้งานจริงไม่ได้ การพัฒนา Simplicity ที่ใช้งานได้จริงเกี่ยวข้องกับการใช้ประโยชน์จากโครงสร้างเชิงคำนวณเพื่อให้นิพจน์กระชับ บทถัดไปสำรวจโครงสร้างข้อมูล การโต้ตอบกับธุรกรรม และ combinator เพิ่มเติม

## การสร้างชนิดข้อมูล

<chapterId>9981ae62-ae50-4770-adf2-b253d1e08de3</chapterId>

ในบทก่อนหน้า เราแสดงให้เห็นว่า combinator แกนหลักของ Simplicity เพียงพอสำหรับ implement การคำนวณบริสุทธิ์แบบจำกัดใด ๆ บทนี้แสดงวิธีสร้างโครงสร้างข้อมูลและการคำนวณที่ใช้งานได้จริงจาก primitive เหล่านี้ — แบบเดียวกับที่คอมพิวเตอร์ถูกสร้างจาก logic gates

### ตรรกะบูลีน

ชนิด Boolean ซึ่งเขียนเป็น `𝟚` เท่ากับ `𝟙 + 𝟙` และมีสองค่า: `σᴸ⟨⟩` (false) และ `σᴿ⟨⟩` (true) ด้วย combinator แกนหลัก เราสามารถสร้างตัวดำเนินการตรรกะบูลีนได้

#### ปฏิบัติการ And

ปฏิบัติการตรรกะ `and : 𝟚 × 𝟚 ⊢ 𝟚` รับสองบิตและคืนหนึ่งบิต การ implement branch ตามบิตแรก: ถ้า false ให้คืน false; มิฉะนั้นให้คืนบิตที่สอง

```
and ≔ case (injl unit) (drop iden) : 𝟚 × 𝟚 ⊢ 𝟚
```

ทดสอบด้วย `⟨false, false⟩`:

```
⟦and⟧⟨false, false⟩
 = {expand the notation for false}
⟦and⟧⟨σᴸ⟨⟩, σᴸ⟨⟩⟩
 = {expand the definition of and}
⟦case (injl unit) (drop iden)⟧⟨σᴸ⟨⟩, σᴸ⟨⟩⟩
 = {evaluate case for σᴸ}
⟦injl unit⟧⟨⟨⟩, σᴸ⟨⟩⟩
 = {evaluate injl}
σᴸ(⟦unit⟧⟨⟨⟩, σᴸ⟨⟩⟩)
 = {evaluate unit}
σᴸ⟨⟩
 = {by the notation for false}
false
```

ทดสอบด้วย `⟨true, true⟩`:

```
⟦and⟧⟨true, true⟩
 = {expand the notation for true and the definition of and}
⟦case (injl unit) (drop iden)⟧⟨σᴿ⟨⟩, σᴿ⟨⟩⟩
 = {evaluate case for σᴿ}
⟦drop iden⟧⟨⟨⟩, σᴿ⟨⟩⟩
 = {evaluate drop}
⟦iden⟧(σᴿ⟨⟩)
 = {evaluate iden}
σᴿ⟨⟩
 = {by the notation for true}
true
```

#### ปฏิบัติการตรรกะอื่น ๆ

ปฏิบัติการ `not` ต้องใช้ combinator ช่วย:

```
                   f : A ⊢ C    g : B ⊢ C
--------------------------------------------------------------
copair f g ≔ iden ▵ unit ⨾ case (take f) (take g) : A + B ⊢ C
```

`iden ▵ unit : A ⊢ A × 𝟙` เริ่มต้นด้วยการเพิ่ม "environment" ว่างให้กับอินพุต ทำให้ combinator `case` ใช้งานได้ การใช้ `take` ในสอง branch จะทิ้ง environment ว่างนี้เพื่อเรียกใช้ `f` หรือ `g`

ปฏิบัติการตรรกะ Boolean อื่น ๆ:

- `or ≔ case (drop iden) (injr unit) : 𝟚 × 𝟚 ⊢ 𝟚`
- `not ≔ copair (injr unit) (injl unit) : 𝟚 ⊢ 𝟚`
- `xor ≔ case (drop iden) (drop not) : 𝟚 × 𝟚 ⊢ 𝟚`

### Bit Adders

"half-adder" รับสองบิตและบวกมัน สร้างเอาต์พุตสองบิต: บิต carry และบิต sum

```
half-adder ≔ and ▵ xor : 𝟚 × 𝟚 ⊢ 𝟚 × 𝟚
```

"full-adder" บวกสามบิต สร้างเอาต์พุตสองบิต อินพุตใช้ tuple ซ้อน `(𝟚 × 𝟚) × 𝟚`

สำหรับ tuple ซ้อน จะใช้สัญกรณ์แบบกระชับ:

- `O f` หมายถึง `take f`
- `I f` หมายถึง `drop f`
- `H` หมายถึง `iden`

ตัวอย่างเช่น `I O H` หมายถึง `drop (take iden) : A × (B × C) ⊢ B` ซึ่งดึงค่าตรงกลาง สัญกรณ์นี้ชวนให้นึกถึงเลขฐานสอง: เมื่อคิดถึง tuple ซ้อนเป็น binary tree สัญกรณ์นี้แทนเลขฐานสองแบบกลับด้านของตำแหน่งในต้นไม้ นิพจน์เหล่านี้ก่อรูปเป็น De Bruijn indices สำหรับ Simplicity

**หมายเหตุ:** สัญกรณ์ `I`, `O` และ `H` ใช้ได้เฉพาะกับ subexpression ที่ประกอบด้วย `take`, `drop` และ `iden` เท่านั้น

full-adder ประกอบ half-adder สองตัวเข้าด้วยกัน โดยนำ logical `or` ของบิต carry:

```
full-adder ≔ take half-adder ▵ I H
           ⨾ O O H ▵ (O I H ▵ I H ⨾ half-adder)
           ⨾ (O H ▵ I O H ⨾ or) ▵ I I H
           : (𝟚 × 𝟚) × 𝟚 ⊢ 𝟚 × 𝟚
```

ในบรรทัดแรก `take half-adder ▵ I H : (𝟚 × 𝟚) × 𝟚 ⊢ (𝟚 × 𝟚) × 𝟚` เรียก half-adder บนสองบิตแรกและเก็บบิตสุดท้ายไว้

ในบรรทัดที่สอง `O O H ▵ (O I H ▵ I H ⨾ half-adder) : (𝟚 × 𝟚) × 𝟚 ⊢ 𝟚 × (𝟚 × 𝟚)` เก็บบิตแรกไว้ (carry-out ของ half-adder ตัวแรก) และเรียก half-adder บนสองบิตสุดท้าย

ในบรรทัดสุดท้าย `(O H ▵ I O H ⨾ or) ▵ I I H: 𝟚 × (𝟚 × 𝟚) ⊢ 𝟚 × 𝟚` นำ logical OR ของสองบิตแรก (carry-outs ของ half-adder ทั้งสองตัว) และคืนบิต sum-out ของ half-adder ตัวที่สอง

สิ่งนี้สาธิตการเขียนโปรแกรม Simplicity: ใช้สัญกรณ์ `I`, `O` และ `H` เพื่ออ้างอิงบิตข้อมูล สร้าง "environments" ที่เหมาะสมสำหรับเรียกฟังก์ชันอื่นผ่านการประกอบแบบตามลำดับ

ผู้ใช้ไม่ได้กำหนดปฏิบัติการระดับต่ำโดยตรง ตอนต่อ ๆ ไปของชุดนี้จะพูดถึง standard library jets ที่ implement ฟังก์ชันทั่วไป ผู้ใช้ปลายทางไม่ได้ถูกคาดหวังให้เขียนโปรแกรมโดยตรงใน Simplicity คล้ายกับ Bitcoin Script แต่ภาษาระดับสูงอย่าง SimplicityHL จะสร้างโค้ด Simplicity โดยจัดการ "environments" ของ subexpression และแปลตัวแปรที่มีชื่อเป็นลำดับ `take` และ `drop` ที่เหมาะสม

### Vectors

vector ความยาวคงที่ถูกนิยามโดยสร้าง product ของชนิด `A` ซ้ำ:

- `A² ≔ A × A`
- `A⁴ ≔ A² × A²`
- `A⁸ ≔ A⁴ × A⁴`
- `…`

สิ่งเหล่านี้อาจเขียนเป็น `A^2`, `A^4`, `A^8` เป็นต้น

vector ถูกนิยามเฉพาะสำหรับความยาวที่เป็นเลขยกกำลังของสอง ความยาวกำลังอื่นต้องเลือก convention การใส่วงเล็บ

เมื่อมีนิพจน์ `f : A ⊢ B` การจับคู่ซ้ำ ๆ จะ "map" มันไปบน vector ความยาวคงที่:

- `f² ≔ f ▵ f : A² ⊢ B²`
- `f⁴ ≔ f² ▵ f² : A⁴ ⊢ B⁴`
- `f⁸ ≔ f⁴ ▵ f⁴ : A⁸ ⊢ B⁸`

เมื่อมีฟังก์ชัน `f : A × B ⊢ B` การวนซ้ำหรือ "folding" เหนือ vector ความยาวคงที่:

- `fold-right-2 f ≔ O O H ▵ (O I H ▵ I H ⨾ f) ⨾ f : A² × B ⊢ B`
- `fold-right-4 f ≔ fold-right-2 (fold-right-2 f) : A⁴ × B ⊢ B`
- `fold-right-8 f ≔ fold-right-2 (fold-right-4 f) : A⁸ × B ⊢ B`

มี variation มากมาย เมื่อมี `f : A × B ⊢ C`, "zip" เหนือ vector ที่จับคู่กันด้วย `zip-n f : (Aⁿ × Bⁿ) ⊢ Cⁿ` เมื่อมี `f : (A × B) × C ⊢ C`, fold เหนือ vector ที่จับคู่กันด้วย `bifold-right-n f : (Aⁿ × Bⁿ) ⊢ C` การรวม `map` กับ `fold-right` สร้าง combinator แบบสะสม: `f : A × C ⊢ C × B` ให้ `map-accum-right-n f : Aⁿ × C ⊢ C × Bⁿ` ยังมี variant ได้อีกมาก

#### คำหลายบิต

bit vector ให้จำนวนเต็มหลายบิต ตัวอย่างเช่น `𝟚³²` คือชนิด word 32 บิต `𝟚²⁵⁶` คือชนิด word 256 บิต เหมาะสำหรับ hash และปฏิบัติการเข้ารหัสลับ

ด้วย full-adder, variant ของปฏิบัติการ vector นิยาม "ripple carry adder" เหนือ word หลายบิต:

```
full-adder-n ≔ zip-accum-right-n full-adder : (𝟚ⁿ × 𝟚ⁿ) × 𝟚 ⊢ 𝟚 × 𝟚ⁿ
```

`full-adder-n` รับเลขฐานสอง n บิตสองตัวและ carry-input หนึ่งบิต แล้วคืน flag carry-out หนึ่งบิตและผลรวม n บิต

#### SHA-256

ด้วยการนิยามปฏิบัติการเลขคณิตบน word หลายบิตแบบ recursive — การลบ การคูณ การหาร — และปฏิบัติการตรรกะระดับบิต เช่น logical AND, OR, XOR และการรวมสิ่งเหล่านี้ซ้ำ ๆ แม้แต่ฟังก์ชัน block compression ของ SHA-256 ก็สามารถสร้างได้:

```
sha256-hash-block ≔ … : 𝟚²⁵⁶ × 𝟚⁵¹² ⊢ 𝟚²⁵⁶
```

compression ของ SHA-256 ถูกนิยามอย่างเป็นทางการโดยใช้ Simplicity ภายใน proof assistant Rocq (เดิมคือ Coq) พร้อม formal proof ว่า implementation `sha256-hash-block` ถูกต้อง

compression ทำงานช้าเกินไปใน Simplicity ดิบ Jets เรียกใช้ฟังก์ชันทั่วไปอย่าง SHA-256 compression แบบ native implementation ของ Simplicity บริสุทธิ์ทำหน้าที่เป็น formal specifications สำหรับ jets

### Option Types

option type เกิดจากการนำ sum กับ unit type:

```
Option A ≔ 𝟙 + A
```

ชนิด `Option A` อาจเขียนเป็น `A?` หรือ `𝕊 A` (โดย `𝕊` หมายถึง "successor") ฟังก์ชัน map เหนือ option type:

```
                 f : A ⊢ B
------------------------------------------
f? ≔ copair (injl unit) (injr f) : A? ⊢ B?
```

สามารถนิยาม monadic combinator เช่น bind ได้:

```
              f : A ⊢ B?
---------------------------------------
bind f ≔ copair (injl unit) f : A? ⊢ B?
```

### Variable Length Buffers

"Buffers" คือชนิดสำหรับ vector ที่เติมบางส่วน:

- `Aᑉ² ≔ A?`
- `Aᑉ⁴ ≔ A²? × Aᑉ²`
- `Aᑉ⁸ ≔ A⁴? × Aᑉ⁴`
- `…`

ชนิด `Xᑉ⁸` ขยายเป็น `(1 + X⁴) × ((1 + X²) × (1 + X))` เมื่อมองสิ่งนี้เป็น polynomial แล้วขยาย จะได้ `1 + X + X² + X³ + X⁴ + X⁵ + X⁶ + X⁷` เมื่อตีความเป็นชนิดข้อมูล มันแทน sum ของ tuple ของ X ที่เป็นไปได้ทั้งหมดถึง 7 ตัว รวมถึง empty tuple นี่คือชนิดของ list ที่มีความยาวน้อยกว่า 8 อย่างแม่นยำ

เช่นเดียวกับ vector ปฏิบัติการ mapping และ folding สามารถนิยามเหนือ buffer ได้ ปฏิบัติการ stack ได้แก่ `push-<n : Aᑉⁿ × A ⊢ Aⁿ + Aᑉⁿ` และ `pop-<n : Aᑉⁿ ⊢ (Aᑉⁿ × A)?` `push-<n` เพิ่ม item ต่อท้าย buffer โดยคืน vector เต็มหากเกิด overflow `pop-<n` ลบ item ออก โดยคืน buffer ที่เล็กลงและ item ที่ถูกลบ หรืออาจคืน nothing หาก buffer เดิมว่าง

นิยาม `push-<n` แบบ recursive:

```
push-<2 ≔ case (drop (injr (injr iden))) (injl iden)

push-<4 ≔ ((O I H ▵ IH) ⨾ push-<2) ▵ O O H
        ⨾ case (I H ▵ O H ⨾ case (injr (injr (I H) ▵ injl unit)) (injl iden))
               (injr (I H ▵ O H))

push-<8 ≔ ((O I H ▵ IH) ⨾ push-<4) ▵ O O H
        ⨾ case (I H ▵ O H ⨾ case (injr (injr (I H) ▵ (injl unit ▵ injl unit))) (injl iden))
               (injr (I H ▵ O H))

…
```

Simplicity ดิบยากต่อการติดตามเมื่อเกินระดับความซับซ้อนบางอย่าง ผู้ใช้ปลายทางใช้ภาษาระดับสูงอย่าง SimplicityHL ที่สร้างนิพจน์ idiomatic เหล่านี้

### สรุป

บทนี้แสดงวิธีสร้างปฏิบัติการตรรกะจากบิต จากสิ่งเหล่านี้ เลขคณิตระดับบิตเกิดขึ้น ทำให้สามารถให้เหตุผลเกี่ยวกับการทำงานได้ มีการพัฒนา vector type ซึ่งสาธิตการวนซ้ำเหนือ word หลายบิตเพื่อกำหนดเลขคณิต ต่อไป ปฏิบัติการเข้ารหัสลับอย่าง SHA-256 และการตรวจสอบลายเซ็น Schnorr สามารถนิยามได้โดยใช้ combinator ของ Simplicity เพียงอย่างเดียว — และทั้งหมดถูกนิยามจริงด้วย Simplicity

บทนี้ไม่ใช่คู่มือครบถ้วนของชนิดข้อมูลและปฏิบัติการที่เป็นไปได้ทั้งหมดซึ่งสร้างได้ใน Simplicity แต่แสดงให้เห็นการบรรลุ functionality ที่ใช้งานได้จริงภายในข้อจำกัดของ Simplicity แม้ชนิดข้อมูลจะมีขอบเขตจำกัด แต่ vector, buffer type และปฏิบัติการที่วนซ้ำเหนือโครงสร้างเหล่านี้ซึ่งมีประโยชน์ก็สามารถนิยามได้

specification ของปฏิบัติการใน standard library จริงแตกต่างจากนิยามที่นี่เล็กน้อย ตัวอย่างเช่น full-adder ใช้ 3-way XOR และฟังก์ชันตรรกะ "majority" แทน half-adder สองตัว

ในทางปฏิบัติ โปรแกรม Simplicity ใช้ jets สำหรับปฏิบัติการเลขคณิตและเข้ารหัสลับ อย่างไรก็ตาม jets แทนที่ได้เฉพาะนิพจน์เท่านั้น Combinator ที่วนซ้ำเหนือ buffer และ vector ไม่สามารถถูกแทนที่ด้วย jets ได้ และปรากฏในโปรแกรม Simplicity จริง แม้ผู้ใช้ปลายทางจะไม่ได้ใช้สิ่งเหล่านี้โดยตรง แต่ใช้ภาษาระดับสูงอย่าง SimplicityHL ที่สร้างนิพจน์ดังกล่าว

combinator ที่นิยามแบบ recursive ดูเหมือนจะเติบโตแบบ exponential ในขนาดนิพจน์ เรื่องนี้ไม่เป็นปัญหา ระหว่าง serialization นิพจน์ถูกเข้ารหัสเป็น DAGs (directed acyclic graphs) แทนที่จะเป็นต้นไม้ representation จริงจึงเติบโตเพียงเชิงเส้น

จนถึงตอนนี้ เราพิจารณาเฉพาะการคำนวณบริสุทธิ์ การโต้ตอบกับข้อมูลธุรกรรมสำหรับงานอย่างการลงนามธุรกรรมต้องมีวิธีบางอย่างให้โปรแกรม fail หากลายเซ็นไม่ถูกต้อง บทถัดไปพูดถึง side-effects ใน Simplicity

## Side Effects สองแบบ

<chapterId>9eafe498-0765-419a-a69d-a74a9cdf3713</chapterId>

ในบทก่อนหน้า เราแสดงให้เห็นวิธีสร้างโครงสร้างข้อมูลและการคำนวณบางอย่างโดยใช้ชุด combinator แกนหลักของ Simplicity ดังที่เราระบุไว้ combinator แกนหลักเพียงพอสำหรับ implement การคำนวณบริสุทธิ์แบบจำกัดใด ๆ สิ่งนี้ทำให้เกิดคำถามว่า: ยังทำอะไรได้มากกว่านี้อีก? เราสามารถเพิ่ม side effects เพิ่มเติมให้กับนิพจน์ของเราได้

มี side effects ที่เป็นไปได้หลายชนิดสำหรับนิพจน์: การอัปเดตสถานะ, การเขียนลง log, การโยน exception, การอ่านจาก environment, การเรียก continuation ฯลฯ side effects ที่มีใน Simplicity จะขึ้นกับแอปพลิเคชัน

สำหรับแอปพลิเคชัน Bitcoin และ Liquid ปัจจุบันเรามี side effects สองแบบ: Failure effect ซึ่งเป็น exception effect ที่ exception มีชนิด `𝟙`, และ Reader effect ซึ่งอนุญาตให้เข้าถึงข้อมูลจาก transaction environment ได้ combinator แกนหลักของเราเป็น "pure"; มันไม่มี side effects อย่างไรก็ตาม jets สามารถนำ primitive ใหม่ที่มี side effects เข้ามาได้

### Jets ที่มี Effects

เราจะพูดถึง jets เพิ่มเติมภายหลังในหลักสูตรนี้ แต่ที่นี่เราจะแนะนำ jets ตัวอย่างบางตัวเพื่อแสดง side effects ของมัน

#### Bip0340-verify

`bip0340-verify : (𝟚²⁵⁶ × 𝟚²⁵⁶) × 𝟚⁵¹² ⊢ 𝟙` เป็น jet สำหรับนิพจน์ที่รับ x-only pubkey, ข้อความ 256 บิต และลายเซ็น Schnorr แล้วไม่คืนอะไรเลย! ตามชนิดของมัน มันควรทำงานเหมือนกับ `unit` ความแตกต่างอยู่ที่ side effect ของ jet: หากการตรวจสอบลายเซ็นล้มเหลว การคำนวณทั้งหมดจะถูกยกเลิกโดยการโยน exception (ชนิด unit) นี่คือ Failure effect

#### Verify

`verify : 𝟚 ⊢ 𝟙` เป็น jet แบบพื้นฐานสำหรับแสดง Failure effect หากอินพุตของ `verify` เป็น `false` การคำนวณทั้งหมดจะถูกยกเลิกโดยการโยน exception หากอินพุตเป็น `true` จะไม่มีสิ่งใดถูกคืน แต่การคำนวณสามารถดำเนินต่อได้

#### Transaction Hashes

`sig-all-hash : 𝟙 ⊢ 𝟚²⁵⁶` ดูเหมือนเป็นฟังก์ชันคงที่ เพราะมีค่าอินพุตที่เป็นไปได้เพียงค่าเดียว: empty tuple อย่างไรก็ตาม jet นี้อ่านจาก transaction environment และสร้าง hash ของข้อมูลธุรกรรมที่คล้ายกับ message digest `SIGHASH_ALL` ที่ใช้ในการตรวจสอบลายเซ็นของ Bitcoin Script นี่คือตัวอย่างของ Reader effect: ค่าที่คืนขึ้นกับ transaction environment ที่ jet ถูกเรียกใช้ภายใน ยังมี hashing jets อื่นอีกหลายตัวที่ hash subset ต่าง ๆ ของข้อมูล transaction environment เพื่อช่วยสร้าง message digest แบบกำหนดเองสำหรับลายเซ็น

#### Introspection Jets

`input-sequence : 𝟚³² ⊢ 𝟚³²?` เป็นฟังก์ชันที่รับ input index และคืน sequence number ของธุรกรรมสำหรับอินพุตนั้น โดยอาจคืน nothing หาก index อยู่นอกขอบเขต อีกครั้ง ค่าเอาต์พุตไม่ใช่ฟังก์ชันบริสุทธิ์ของ input index แต่ปฏิบัติการใช้ Reader effect เพื่อเข้าถึง transaction environment เพื่อกำหนดค่าเอาต์พุต ยังมี introspection jets อื่นอีกหลายตัวที่คืน fragment ต่าง ๆ ของข้อมูล transaction environment

### การจำแนก Effects

side effects ไม่ได้ถูกสร้างมาเท่ากันทั้งหมด side effects บางชนิดมีพฤติกรรมเรียบร้อยกว่าชนิดอื่น เราสามารถจำแนก effects ตามความเหมาะสมต่อการแปลงโปรแกรมได้

#### Commutative Effects

commutative effect คือ effect ที่หากคุณสลับเอาต์พุตของนิพจน์สองตัว คุณสามารถสลับนิพจน์เองได้อย่างปลอดภัยโดยไม่เปลี่ยน effect ของนิพจน์ พิจารณา `swap = I H ▵ O H : A × B ⊢ B × A` หาก `f ▵ g ⨾ swap = g ▵ f` สำหรับทุกนิพจน์ `f` และ `g` ที่มี side effects แล้ว effects นั้นเป็น commutative

การอ่านข้อมูลธุรกรรมจาก environment เป็น commutative effect เพราะผลของการอ่านจาก environment เหมือนกัน ไม่ว่าเราจะ execute การอ่านในลำดับใด

โดยทั่วไป การโยน exception ไม่ใช่ commutative effect หาก `f` โยน exception บางตัว `e₁` และ `g` โยน exception อีกตัว `e₂` แล้ว exception ใดถูกโยนจากคู่ของ `f` และ `g` จะขึ้นกับลำดับที่มันถูก execute

อย่างไรก็ตาม ในกรณีพิเศษของ Failure effect ซึ่งโยนได้เฉพาะ exception ชนิด unit, effect นี้เป็น commutative ไม่ว่า `f` หรือ `g` ตัวใดจะโยน exception, exception ที่ได้จะเหมือนกัน เพราะมีค่า exception ที่เป็นไปได้เพียงค่าเดียว

#### Idempotent Effects

idempotent effect คือ effect ที่หากคุณทำซ้ำเอาต์พุตของนิพจน์ คุณสามารถทำซ้ำนิพจน์เองได้อย่างปลอดภัยโดยไม่เปลี่ยน effect ของนิพจน์ พิจารณา `dup = iden ▵ iden : A ⊢ A × A` หาก `f ⨾ dup = dup ⨾ f ▵ f` สำหรับทุก `f` ที่มี side effects แล้ว effects นั้นเป็น idempotent

การอ่านข้อมูลธุรกรรมจาก environment เป็น idempotent effect การโยน exception ก็เป็น idempotent effect เช่นกัน แม้ว่าจะมีเพียงหนึ่งในสองนิพจน์ที่ถูกทำซ้ำเท่านั้นที่จะถูก execute แต่ exception ใด ๆ ที่ถูกโยนโดย `dup ⨾ f ▵ f` จะเหมือนกับ exception ที่ถูกโยนโดย `f ⨾ dup`

อย่างไรก็ตาม การเขียนลง log อาจไม่เป็น idempotent เพราะการทำ effect ซ้ำจะทำให้ข้อความ log ปรากฏสองครั้ง แต่หาก log ประกอบด้วย _set_ ของข้อความแทน _list_ ของข้อความ effect ก็จะเป็น idempotent (และ commutative) เพราะการ insert ลง set เองเป็นปฏิบัติการ idempotent

#### Unitary Effects

unitary effect คือ effect ที่หากคุณทิ้งเอาต์พุตของนิพจน์ คุณสามารถทิ้งนิพจน์เองได้อย่างปลอดภัยโดยไม่เปลี่ยน effects ของนิพจน์ หากเป็นจริงเสมอว่า `f ⨾ unit = unit` สำหรับทุก `f` ที่มี side effects แล้ว effects ของคุณเป็น unitary

การอ่านข้อมูลจาก environment เป็นหนึ่งใน side effects ไม่กี่ชนิดที่เป็น unitary หากผลของการอ่านข้อมูลธุรกรรมจาก environment ถูกทิ้ง นิพจน์ทั้งหมดที่ทำการอ่านอาจถูกทิ้งได้

failure effect ไม่เป็น unitary หาก `f` โยน exception แล้ว `f ⨾ unit` ก็จะโยนด้วย; execution จะไปไม่ถึง combinator `unit` ก่อนที่การคำนวณจะถูกยกเลิกด้วยซ้ำ ในทางกลับกัน `unit` ชัดเจนว่าจะไม่โยน exception ใด ๆ ดังนั้น effects ของ `f ⨾ unit` และ `unit` จะแตกต่างกัน

สรุปแล้ว นี่คือผลของ effects ที่พูดถึงข้างต้นเมื่อเทียบกับคุณสมบัติทั้งสาม:

| Effect | Commutative | Idempotent | Unitary |
| --- | :---: | :---: | :---: |
| Reader (transaction environment) | ✓ | ✓ | ✓ |
| Failure (unit-typed exception) | ✓ | ✓ | ✗ |
| Writer (log as a set) | ✓ | ✓ | ✗ |
| General exceptions (arbitrary type) | ✗ | ✓ | ✗ |

### Effects ที่อนุญาตใน Simplicity

ยิ่งชนิดของ effect มีคุณสมบัติที่มีพฤติกรรมดีมากเท่าไร optimizer ของ Simplicity ก็ยิ่งมีพื้นที่ในการแปลงโปรแกรมที่ใช้ effects เหล่านั้นมากขึ้นเท่านั้น ในอุดมคติ เราจะอนุญาตเฉพาะ effects ที่มีคุณสมบัติครบทั้งสาม: commutative, idempotent และ unitary สิ่งนี้จะทำให้ optimizer สามารถทำ program transformation ใด ๆ ก็ได้ตามต้องการ อย่างไรก็ตาม การอ่านจาก environment เป็น effect เดียวที่ตอบสนองคุณสมบัติครบทั้งสาม

แทนที่จะทำเช่นนั้น เรากำหนดว่า effects ของ Simplicity ต้องเป็น commutative และ idempotent effects ทั้งสองแบบที่เราใช้ใน Simplicity คือ Failure effect และ Reader effect เป็น commutative และ idempotent สิ่งนี้เปิดให้ทำ optimization จำนวนมากบนโค้ด Simplicity ได้

อย่างไรก็ตาม การแปลงแบบ "discard" ที่อธิบายข้างต้น ซึ่งพยายามแทนที่ `f ⨾ unit` ด้วย `unit` หรือการแปลงใด ๆ ที่คล้ายกัน จะไม่ได้รับอนุญาตหาก `f` อาจสร้าง Failure effect จริง ๆ แล้ว ลองจินตนาการว่า `f` มี assertion `bip0340-verify` อยู่ การพยายาม optimize การตรวจสอบนั้นทิ้งไปจะเป็นหายนะ

### ทำไมต้องอนุญาต Side Effects เลย?

ทำไม Simplicity ถึงอนุญาต side effects ด้วย? จะไม่ดีกว่าหรือถ้าทุกโปรแกรมรับธุรกรรมทั้งหมดเป็นอินพุตและคืนเอาต์พุต Boolean ที่ตัดสินว่าธุรกรรมนั้นถูกต้องหรือไม่?

#### Batch Verification

เหตุผลหนึ่งที่เรามี Failure effect คือเพื่อรองรับ [batch verification](https://github.com/bitcoin/bips/blob/c9a6ca6297eb8de850f6b64dafb8e60ee9b64d66/bip-0340.mediawiki#batch-verification) ของลายเซ็น Schnorr ใน batch verification การตรวจสอบลายเซ็น Schnorr แต่ละรายการจำนวนมากถูกรวมเข้าด้วยกันในลักษณะที่หากการตรวจสอบลายเซ็นใดลายเซ็นหนึ่งล้มเหลว batch ทั้งหมดจะล้มเหลว

ขั้นตอน batching นี้เพิ่มประสิทธิภาพเมื่อเทียบกับการตรวจสอบลายเซ็นทีละรายการ ข้อเสียคือหาก batch verification ล้มเหลว เราจะไม่รู้ว่าการตรวจสอบลายเซ็นใดหรือชุดใดล้มเหลว

ด้วยการใช้ failure side effect, `bip0340-verify` รับประกันว่าหากการตรวจสอบลายเซ็นล้มเหลว ธุรกรรมทั้งหมดจะล้มเหลว หาก `bip0340-verify` คืน `𝟚` ซึ่งเป็นชนิด Boolean แทน สำหรับ success หรือ failure การตรวจสอบลายเซ็นที่ล้มเหลวอาจยังนำไปสู่ branch ที่ script สำเร็จได้ ในกรณีเช่นนั้น เราจะต้องรู้ว่าลายเซ็นเฉพาะนั้นถูกต้องหรือไม่ และดังนั้นเราจะไม่สามารถใช้ประโยชน์จาก batch verification ได้

#### ข้อมูลธุรกรรมที่คำนวณล่วงหน้า

ปัญหาใน Bitcoin Script ยุคแรกคือฟังก์ชัน hashing ที่ใช้สร้าง message digest สำหรับลายเซ็นเป็นเชิงเส้นตามขนาดของธุรกรรม โดยทั่วไปทุกอินพุตสร้าง message digest อย่างน้อยหนึ่งตัวสำหรับการตรวจสอบลายเซ็น ดังนั้นโดยรวมแล้วปริมาณ hashing จึงเป็น quadratic ตามขนาดธุรกรรม

ปัญหานี้ถูกแก้ใน Segwit และ iteration ถัดมาของ Bitcoin Script โดยนิยาม message digest ใหม่ให้คำนวณได้ในเวลาคงที่ต่อการตรวจสอบลายเซ็นหนึ่งครั้ง สิ่งนี้อาศัยการมี `PrecomputedTransactionData` ซึ่ง precompute hash ของข้อมูลธุรกรรมครั้งเดียวแล้วแชร์โดยการคำนวณ sighash ของแต่ละอินพุต transaction hashing jets ของ Simplicity อาศัยข้อมูลธุรกรรมที่คำนวณล่วงหน้าแบบเดียวกันเพื่อให้แน่ใจว่า jets ทำงานในเวลาคงที่

สมมติว่า `sig-all-hash` ไม่ใช้ Reader effect สมมติว่าเราจัดการสร้างชนิด Simplicity สำหรับ transaction environment ได้ เรียกมันว่า `TxEnv` เพื่อให้ `sig-all-hash : TxEnv ⊢ 𝟚²⁵⁶` เป็นชนิดของ jet นิยามดังกล่าวจะกำหนดให้ jet `sig-all-hash` ต้องสามารถคำนวณ hash ของธุรกรรมใด ๆ ได้ ไม่ใช่แค่ธุรกรรมที่มันเกี่ยวข้อง โปรแกรม Simplicity สามารถคัดลอก `TxEnv` ที่ได้รับและส่งสำเนาที่แก้ไขแล้วให้ `sig-all-hash` ได้ ในกรณีเช่นนี้ `sig-all-hash` จะพึ่งพา `PrecomputedTransactionData` ไม่ได้ และเราจะกลับไปต้องใช้เวลาเชิงเส้นตามข้อมูลธุรกรรมใดก็ตามที่ถูกส่งเข้าไปใน `sig-all-hash` เวอร์ชันนี้

เพราะ `sig-all-hash : 𝟙 ⊢ 𝟚²⁵⁶` ใช้ Reader effect เพื่อเข้าถึงข้อมูลธุรกรรม มันจึงเข้าถึงได้ _เฉพาะ_ transaction environment คงที่ ด้วยเหตุผลนั้น implementation ของ jet จึงสามารถใช้ `PrecomputedTransactionData` ได้อย่างปลอดภัยและทำงานในเวลาคงที่

### Cross-Input Signature Aggregation

แม้ทั้ง Liquid และ Bitcoin ยังไม่รองรับ [cross-input signature aggregation](https://hrf.org/latest/cisa-research-paper/) ณ เวลานี้ เราต้องการตรวจสอบว่า Simplicity จะเข้ากันได้กับมันเมื่อถึงเวลา

แม้รายละเอียดยังไม่ได้ถูกกำหนด เราจินตนาการว่า half-aggregation จะถูก implement ด้วย Writer effect นั่นคือ jet ใหม่ที่มีชนิดอย่าง `half-agg-verify : (𝟚²⁵⁶ × 𝟚²⁵⁶) × 𝟚²⁵⁶ ⊢ 𝟙` จะรับ public key, message digest และ `r`-component ของลายเซ็น Schnorr (ลายเซ็น Schnorr ประกอบด้วย `r`-component และ `s`-component) แล้วเขียนมันลง transaction log ก่อนดำเนินการต่อ จากนั้น ที่อื่นในธุรกรรมหรือพร้อมกับธุรกรรม จะมี aggregate `s`-component สำหรับลายเซ็น Schnorr ที่ถูก half-aggregate ทั้งหมด ธุรกรรมจะ valid ก็ต่อเมื่อมี aggregate `s`-component ดังกล่าวสำหรับ key, message และ `r`-component ทั้งหมดที่ถูก log

เพื่อให้เป็นไปตามข้อกำหนดของ Simplicity, Writer effect นี้ต้องเป็น idempotent และ commutative สิ่งนี้รับประกันได้ด้วยการปฏิบัติต่อ writer log เป็น set ของ tuple ของ key, message และ `r`-component วิธีนี้ใช้ได้เพราะ set operations เป็น idempotent และ commutative การปฏิบัติต่อ log เป็น set ของค่าจะเข้ากันได้กับอัลกอริทึมการตรวจสอบ half-aggregation

### สรุป

ในบทนี้ เราดูการเพิ่ม side effects ให้กับการคำนวณที่ Simplicity ทำได้ เราจำแนก effect หลายชนิดตามว่ามันมีพฤติกรรมดีเพียงใดเมื่อเทียบกับ program transformation หลายชนิด เราตัดสินใจจำกัด effects ของ Simplicity ให้เป็นชนิดที่ commutative และ idempotent

effects สองแบบที่เราใช้สำหรับแอปพลิเคชัน Bitcoin และ Liquid คือ Reader effect สำหรับเข้าถึง transaction environment และ Failure effect สำหรับยกเลิกและทำให้โปรแกรมล้มเหลว jets บางตัวใช้ primitive operations ที่ side effects ลักษณะเหล่านี้สามารถเกิดขึ้นได้

Failure effect กำหนดเอาต์พุตของโปรแกรม Simplicity: โปรแกรมล้มเหลว ทำให้ธุรกรรม invalid หรือโปรแกรมสำเร็จ Reader effect ให้ input ชนิดหนึ่งแก่โปรแกรม Simplicity: environment ที่มีข้อมูลธุรกรรม แต่เรายังต้องให้ input อื่น เช่น ลายเซ็นดิจิทัล แก่โปรแกรม Simplicity ด้วย

ในบทถัดไป เราจะดูว่าโปรแกรม Simplicity คืออะไร มันถูกแปลงเป็นที่อยู่อย่างไร และเราเพิ่ม input อื่น ๆ เช่น ลายเซ็น เข้าไปในโปรแกรม Simplicity อย่างไร

## โปรแกรมและที่อยู่

<chapterId>961652e3-8f7d-4c2a-8b55-9a990b91a0dd</chapterId>

ในบทก่อนหน้า เราอธิบาย side effects สองแบบที่ใช้ใน Simplicity: Failure effect ซึ่งกำหนดความสำเร็จหรือความล้มเหลวของโปรแกรม และ Reader effect ซึ่งให้การเข้าถึง transaction environment ตอนนี้เราหันไปสู่คำถามเชิงปฏิบัติ: โปรแกรม Simplicity คืออะไรกันแน่ และมันกลายเป็นที่อยู่บนบล็อกเชนได้อย่างไร?

### โปรแกรม Simplicity

โปรแกรม Simplicity ถูกนิยามเป็นนิพจน์ Simplicity ที่มีชนิด `𝟙 ⊢ 𝟙` type signature นี้หมายความว่าโปรแกรมไม่รับอินพุตที่มีความหมาย (เพียงค่า unit) และไม่สร้างเอาต์พุตที่มีความหมาย (เพียงค่า unit) Reader effect จับ input ของ transaction environment ในขณะที่ Failure effect บ่งชี้ success หรือ failure effects เหล่านี้จัดการ I/O แทนที่จะเป็นชนิดของ Simplicity เอง

### Commitment Merkle Root

แทนที่จะเก็บโปรแกรมสมบูรณ์บนเชน Bitcoin ใช้ commitments — แนวปฏิบัติที่ต่อยอดจาก Pay-to-Script-Hash (P2SH) Simplicity ใช้ Commitment Merkle Root (CMR)

combinator แต่ละตัวได้รับ tag SHA-256 ที่ได้จาก pattern: `Simplicity␟Commitment␟[identifier]` โดย `␟` แทน ASCII code 31 (unit separator)

แต่ละ tag คือ hash SHA-256 ของ pre-image string ที่เกี่ยวข้องซึ่งแสดงด้านล่าง:

| Combinator | Tag pre-image (ASCII string) |
|---|---|
| `iden` | `Simplicity␟Commitment␟iden` |
| `unit` | `Simplicity␟Commitment␟unit` |
| `comp` | `Simplicity␟Commitment␟comp` |
| `pair` | `Simplicity␟Commitment␟pair` |
| `case` | `Simplicity␟Commitment␟case` |
| `take` | `Simplicity␟Commitment␟take` |
| `drop` | `Simplicity␟Commitment␟drop` |
| `injl` | `Simplicity␟Commitment␟injl` |
| `injr` | `Simplicity␟Commitment␟injr` |

จากนั้นนิพจน์ Simplicity จะถูก hash แบบ recursive เป็น CMR 256 บิต โดยคำนวณ tagged SHA-256 midstate สำหรับแต่ละ combinator ร่วมกับ CMRs ของ argument ของมัน (เขียน `#ᶜ(e)` สำหรับ CMR ของนิพจน์ `e`, และ `∥` สำหรับ byte concatenation):

| Combinator | กฎ CMR |
|---|---|
| `iden` | `#ᶜ(iden) = SHA-256-midstate(tag_iden ∥ tag_iden)` |
| `unit` | `#ᶜ(unit) = SHA-256-midstate(tag_unit ∥ tag_unit)` |
| `comp f g` | `#ᶜ(comp f g) = SHA-256-midstate(tag_comp ∥ tag_comp ∥ #ᶜ(f) ∥ #ᶜ(g))` |
| `pair f g` | `#ᶜ(pair f g) = SHA-256-midstate(tag_pair ∥ tag_pair ∥ #ᶜ(f) ∥ #ᶜ(g))` |
| `case f g` | `#ᶜ(case f g) = SHA-256-midstate(tag_case ∥ tag_case ∥ #ᶜ(f) ∥ #ᶜ(g))` |
| `take f` | `#ᶜ(take f) = SHA-256-midstate(tag_take ∥ tag_take ∥ 32·0x00 ∥ #ᶜ(f))` |
| `drop f` | `#ᶜ(drop f) = SHA-256-midstate(tag_drop ∥ tag_drop ∥ 32·0x00 ∥ #ᶜ(f))` |
| `injl f` | `#ᶜ(injl f) = SHA-256-midstate(tag_injl ∥ tag_injl ∥ 32·0x00 ∥ #ᶜ(f))` |
| `injr f` | `#ᶜ(injr f) = SHA-256-midstate(tag_injr ∥ tag_injr ∥ 32·0x00 ∥ #ᶜ(f))` |

binary combinators (`comp`, `pair`, `case`) concatenate CMRs ของ child ทั้งสอง; unary combinators (`take`, `drop`, `injl`, `injr`) concatenate CMR ของ child ตัวเดียวหลัง padding `0x00` จำนวน 32 bytes; และ nullary leaves (`iden`, `unit`) hash tag ของมันเท่านั้น conventions สองข้อทำให้สิ่งนี้คำนวณได้ถูก: ใช้ SHA-256 midstates เพื่อให้ **แต่ละนิพจน์ต้องเรียกฟังก์ชัน SHA-256 compression อย่างมากหนึ่งครั้ง** (สมมติว่า midstate ถึง constant tags ถูก precompute แล้ว), และ constructor แบบหนึ่ง argument prefix argument ของมันด้วย padding `0x00` จำนวน 32 bytes ซึ่งเปิดให้มี precomputation เพิ่มเติมเล็กน้อยสำหรับ implementation ที่ต้องการ

สำหรับ combinator `unit` — constructor แบบ nullary ที่ไม่มี argument sub-expressions — กฎนี้เจาะจงเป็น `#ᶜ(unit) = SHA-256-midstate(tag_unit ∥ tag_unit)` โดย `tag_unit = SHA-256(Simplicity␟Commitment␟unit)` (tag ถูกป้อนเข้าไปสองครั้ง) CMR ที่ได้สำหรับโปรแกรม `unit` แบบ trivial คือ:

```
0xc40a10263f7436b4160acbef1c36fba4be4d95df181a968afeab5eac247adff7
```

ที่สำคัญ CMR ไม่ commit ต่อชนิดของนิพจน์ Simplicity แต่พึ่งพา type inference ระหว่าง redemption แทน

### ที่อยู่

ที่อยู่ใช้กลไก Taproot ของ BIP-0341 โดยมี CMRs ที่ commit ภายใต้ TapLeaf version `0xbe` กระบวนการประกอบด้วย:

1. คำนวณ TapLeaf tagged hash ที่รวม version byte, ความยาว CMR และ CMR เอง
2. tweak public key ภายใน (โดยใช้ NUMS point เมื่อไม่ต้องการ key-spend path)
3. แปลงเป็นรูปแบบ bech32m
4. เพิ่ม checksum ที่เหมาะสม

เมื่อไม่ต้องการ key-spend path, internal public key จะถูกตั้งเป็น **NUMS** ("Nothing-Up-My-Sleeve") point: จุดบนเส้นโค้งที่ถูกเลือกอย่างตั้งใจเพื่อให้ไม่มีใครรู้ discrete logarithm ของมัน — กล่าวอีกอย่าง คือจุดที่ไม่มี private key ที่สอดคล้องกัน เพราะไม่มีใครสามารถสร้างลายเซ็นให้มันได้ key-spend path จึงใช้งานไม่ได้อย่างพิสูจน์ได้ และ output สามารถถูกใช้จ่ายได้ *เฉพาะ* ผ่าน committed Simplicity script path ในแอปพลิเคชันจริง NUMS point นี้ควรถูก randomize ตามคำแนะนำของ BIP-0341 เพื่อให้ output ที่ไม่มี key-spend path แยกไม่ออกจาก Taproot outputs ทั่วไป (ประโยชน์ด้าน privacy)

#### จาก Simplicity สู่ที่อยู่

มาลองเดินผ่านการ derive ทั้งหมดสำหรับโปรแกรมที่ง่ายที่สุดเท่าที่เป็นไปได้: `unit : 𝟙 ⊢ 𝟙`, no-op ที่สำเร็จเสมอ

**1. Combinator tag.** ขั้นแรกคำนวณ tag `unit`:

```
tag_unit = SHA-256(Simplicity␟Commitment␟unit)
         = 0xd723083cff3c75e29f296707ecf2750338f100591c86e0c71717f807ff3cf69d
```

**2. CMR.** ป้อน tag เข้าไปสองครั้งเพื่อให้ได้ CMR ของโปรแกรม:

```
CMR = #ᶜ(unit) = SHA-256-midstate(tag_unit ∥ tag_unit)
    = 0xc40a10263f7436b4160acbef1c36fba4be4d95df181a968afeab5eac247adff7
```

**3. TapLeaf hash.** prefix CMR ด้วย TapLeaf version ของ Simplicity `0xbe` และความยาว CMR `0x20` (32 bytes), จากนั้นใช้ Elements TapLeaf tagged hash (tagged hash คือ `hash_str(x) = SHA-256(SHA-256(str) ∥ SHA-256(str) ∥ x)`):

```
hash_TapLeaf/elements(0xbe ∥ 0x20 ∥ CMR)
  = 0x44cc38311ec7e5dfb7b573baf38449496ecd334eb5509cfed1b4fd30da8dd41c
```

เมื่อมี leaf เดียวนี้เท่านั้น ไม่มี TapBranches ดังนั้น hash นี้จึงเป็น TapTree root แล้ว

**4. TapTweak.** เนื่องจากเราไม่ต้องการ key-spend path เราจึงใช้ BIP-0341 NUMS point เป็น internal key และ tweak มันด้วย TapTree root:

```
internal_pk = 0x50929b74c1a04954b78b4b6035e97a5e078a5a0f28ec96d547bfee9ace803ac0
t = hash_TapTweak/elements(internal_pk ∥ 0x44cc38311ec7e5dfb7b573baf38449496ecd334eb5509cfed1b4fd30da8dd41c)
  = 0xb3bef172389b0937d7e5a8b15cfa41e776777f13f2f659cb06220a6ff0658285
```

**5. Output key.** tweak internal key บน curve, `output_pk = lift_x(internal_pk) ⊕ t·G` (สรุป elliptic-curve arithmetic ไว้ที่นี่) ให้ x-only output key `0x2cb0c20acd7340b4d4b65f6a60e2888d0d64e3267261f3b3cf7290e5af3f9e09`

**6. Bech32m address.** encode x-only output key, prefix `p` (อักขระ witness-version ของ SegWit v1), เพิ่ม Liquid-testnet human-readable prefix `tex1`, และต่อท้าย Bech32m checksum ที่อยู่สุดท้ายคือ:

```
tex1p9jcvyzkdwdqtf49kta4xpc5g35xkfcexwfsl8v70w2gwttelncyshxjk56
```

ทั้งหมดนี้เป็นงานจำนวนมาก — แต่ส่วนมากถูกกำหนดโดย Taproot เอง ไม่ใช่โดย Simplicity

### Witness Expressions

ชนิด combinator ใหม่จัดการการไม่มีอินพุตให้กับโปรแกรม Simplicity: witness expression combinator `witness` อนุญาตให้ข้อมูลลายเซ็นและ witness material อื่นถูกรวมเข้าในโปรแกรม

```
      w : B
-----------------
witness w : A ⊢ B
```

semantics ของ witness expression ตรงไปตรงมา: มันไม่สนใจอินพุตและคืนค่า `w` (ซึ่งอาจเป็นชนิด Simplicity ใด ๆ) กล่าวคือ `⟦witness w⟧(a) = w` สิ่งนี้ไม่ได้เพิ่ม **expressiveness ใหม่** — ตามทฤษฎีบทความสมบูรณ์ Simplicity สามารถสร้างฟังก์ชันคงที่เช่นนี้ได้อยู่แล้ว (นึกถึง macro `scribe` จากบทก่อนหน้า) จุดสำคัญของ combinator `witness` อยู่ที่ **CMR** ของมันทั้งหมด: ค่า `w` ถูก **excluded** จาก CMR ของนิพจน์ ดังนั้นที่อยู่จึงคำนวณได้ก่อนที่ `w` จะถูกรู้ และ `w` ถูกให้มา ณ เวลา redemption

ทางเลือกการออกแบบนี้รองรับ pruning — branch มีเงื่อนไขที่ไม่ได้ถูก execute ไม่จำเป็นต้องถูกเปิดเผยบนเชน รวมถึง witness expressions ที่เกี่ยวข้องกับมันด้วย เมื่อ branch ถูก prune, verifier ต้องการเพียง CMR ของ pruned subtree ไม่ใช่เนื้อหาจริงของมัน

### Witness Values

อาจดูเหมือนเป็นข้อจำกัดที่ witness expression ถือได้เพียง *ค่า* ไม่ใช่นิพจน์ Simplicity ทั่วไปกว่า แต่โปรแกรมสำหรับบล็อกเชนแบบ UTXO ถูก execute เพียงครั้งเดียว ไม่มีความจำเป็นต้องส่ง sub-expression ทั้งก้อนเข้าไปใน witness node: ผู้ใช้สามารถเรียก sub-expression นั้นด้วยตัวเอง off-chain แล้วถอด output ของมันลงเป็น witness value เพื่อให้ได้ผลเดียวกัน

(ภายหลังในหลักสูตรนี้ เราจะพบ combinator `disconnect` ซึ่งทำงานคล้าย witness expression ที่ *รับ* นิพจน์ Simplicity ทั้งก้อนเป็น argument)

การออกแบบทางเลือกหนึ่งคือป้อนข้อมูล witness ทั้งหมดเป็น argument ให้โปรแกรม Simplicity ระดับบนสุด witness expressions เป็นที่นิยมกว่าด้วยเหตุผลสองประการ ประการแรก **pruning**: branch ที่ไม่ได้ถูก execute ของนิพจน์ `case` จะไม่ถูกเปิดเผยบนเชน และ witness expressions ใด ๆ ภายใน branch เหล่านั้นจะถูก prune ออกไปพร้อมกัน ประการที่สอง **locality**: witness expressions ทำให้เราวาง witness value แต่ละค่าได้ตรงจุดที่มันถูกใช้ แทนที่จะต้อง thread มันลงมาจากอินพุตระดับบนสุดของโปรแกรม

### Type Inference

เนื่องจาก CMRs ไม่ commit ต่อชนิด ระบบชนิดข้อมูลจึงถูก reconstructed ระหว่าง redemption อัลกอริทึม type inference ของ Simplicity กำหนดชนิดขั้นต่ำสำหรับแต่ละ subexpression จากโครงสร้าง combinator กล่าวให้แม่นยำกว่านั้น inference คำนวณชนิด *principal* (ทั่วไปที่สุด) ของทุก subexpression; type variables ใด ๆ ที่ยังเหลือ free อยู่จะถูก instantiate เป็น unit type `𝟙` ซึ่งให้ชนิดที่ไม่ซ้ำและน้อยที่สุดสำหรับโปรแกรม

### สรุป

ในบทนี้ เราสถาปนาว่าโปรแกรม Simplicity คือนิพจน์ชนิด `𝟙 ⊢ 𝟙`, อธิบายว่า Commitment Merkle Roots ถูกสร้างจาก tagged SHA-256 hashes ของ combinator แต่ละตัวอย่างไร และแสดงว่า CMRs ถูกแปลงเป็นที่อยู่บนเชนผ่าน BIP-0341 Taproot อย่างไร เราแนะนำ witness expressions ในฐานะกลไกสำหรับให้ข้อมูลลายเซ็นและ input อื่น ๆ ณ เวลาใช้จ่าย โดยไม่ต้อง commit ต่อค่าของมันตอนสร้างที่อยู่
