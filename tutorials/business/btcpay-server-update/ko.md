자체 결제 프로세서를 운영한다는 것은 곧 스스로 보안 팀이 된다는 뜻이기도 합니다. BTCPay Server 유지관리자가 보안 릴리스를 게시해도 아무도 대신 인스턴스를 패치해 주지 않습니다. 업데이트, 검증, 그리고 그 뒤따르는 자격 증명 교체는 모두 직접 수행해야 합니다.

이 튜토리얼은 어떤 방식으로 BTCPay Server를 배포했든 전체 절차를 안내합니다. 실행 중인 버전을 확인하고, 배포 유형에 맞게 업데이트를 적용하며, 업데이트가 실제로 반영되었는지 검증하고, 인스턴스가 취약했던 동안 공격자가 확보했을 수 있는 비밀 정보를 교체합니다.

아직 BTCPay Server를 배포하지 않았다면, 설치 가이드부터 시작하세요:

https://planb.academy/tutorials/business/point-of-sale/btcpay-server-928eb01e-824b-4b57-a3e8-8727633beddc

## 2026년 8월의 치명적 취약점

⚠️ **긴급 보안 경고(2026년 8월 7일):** BTCPay Server에 영향을 미치는 심각한 취약점이 현재 활발히 악용되고 있으며, 자금 손실로 이어질 수 있습니다. `Admin Dashboard > Server > Maintenance > Update`를 통해 즉시 인스턴스를 **버전 2.4.2**로 업데이트한 뒤, 푸터에 `2.4.2`가 표시되는지 확인하십시오. 즉시 업데이트할 수 없다면 BTCPay Server를 종료하십시오. 업데이트 후에는 macaroons와 `macaroons.db`를 완전히 새로 발급하고, 다른 Lightning 백엔드의 인증 문자열도 모두 완전히 새로 발급해야 하며, BTCPay Server 내에서 핫 온체인 지갑을 생성한 적이 있다면 해당 자금을 옮기고 지갑을 다시 생성하십시오. 통합 개발자는 NBXplorer도 버전 2.6.10으로 업데이트해야 합니다. 출처: [BTCPay Server 2.4.2 릴리스 노트](https://github.com/btcpayserver/btcpayserver/releases/tag/v2.4.2).

버전 2.4.2는 2026년 8월 7일에 게시되었습니다. 릴리스 노트에 따르면 이 버전은 Bitcoin Red Team 활동을 통해 `brunoerg`와 `benthecarman`이 보고한, 이미 실제 환경에서 악용되고 있던 치명적 취약점을 수정합니다. 같은 릴리스는 Greenfield Basic 인증을 통한 TOTP 2단계 인증 우회도 수정하며, 계정 생성 5분 후 Greenfield Basic 인증을 기본적으로 비활성화합니다.

"활발히 악용 중"이라는 말에는 두 가지 결과가 따릅니다:

- **업데이트는 선택 사항도 아니고 다음 주로 미룰 일도 아닙니다.** 인터넷에서 접근 가능한 패치되지 않은 인스턴스는 반드시 업데이트하거나 꺼야 합니다.
- **업데이트만으로는 충분하지 않습니다.** 패치 전에 인스턴스가 침해되었다면, 공격자는 이미 Lightning 자격 증명과 BTCPay Server가 생성한 핫 월렛 키 자료의 사본을 가지고 있을 수 있습니다. 이러한 비밀 정보는 교체하기 전까지 업데이트 후에도 계속 유효합니다. 아래의 교체 섹션은 사람들이 건너뛰기 쉬운 부분이지만, 실제로 자금을 보호하는 부분입니다.

## Step 1 — 실행 중인 버전 확인하기

BTCPay Server에 로그인하여 **아무 페이지의 푸터**를 확인하세요. 버전 문자열이 거기에 표시됩니다. 현재 버전과 업데이트 제어 항목이 표시되는 `Admin Dashboard > Server > Maintenance`를 열 수도 있습니다.

인스턴스가 Greenfield API를 노출한다면 `GET /api/v1/server/info`도 버전을 반환합니다.

`2.4.2` 미만은 모두 취약합니다.

## Step 2 — 업데이트하기

### 자체 호스팅 Docker 배포(표준 설치)

이는 공식 Docker 배포를 다룹니다. BTCPay Server 문서, LunaNode 원클릭 런처, 대부분의 VPS 설치에서 사용하는 방식입니다.

가장 간단한 경로는 웹 인터페이스입니다:

1. `Admin Dashboard > Server > Maintenance`로 이동합니다.
2. **Update**를 클릭합니다.
3. 컨테이너가 내려받아지고 재시작될 때까지 기다립니다. 인터페이스는 몇 분 동안 사용할 수 없습니다.

웹 인터페이스에 접근할 수 없거나 로그를 보고 싶다면 SSH로 수행하세요:

```bash
sudo su -
cd "$BTCPAY_BASE_DIRECTORY/btcpayserver-docker"
. ./btcpay-update.sh
```

기본 설치에서 `$BTCPAY_BASE_DIRECTORY`는 `/root`이므로 디렉터리는 `/root/btcpayserver-docker`입니다. 스크립트는 최신 이미지를 가져오고, 컨테이너를 다시 생성하며, 결과 버전을 출력합니다.

Docker 배포에는 BTCPay Server와 함께 NBXplorer가 포함되므로, 표준 업데이트는 NBXplorer도 권장 버전인 `2.6.10`으로 올립니다. NBXplorer를 별도로 실행하는 경우 — 통합 개발자와 맞춤 스택에서 일반적입니다 — 명시적으로 업데이트하세요.

### Umbrel

Umbrel 대시보드를 열고 **App Store**로 이동한 뒤, BTCPay Server를 찾아 업데이트가 제공되면 적용하세요.

⚠️ **중요:** 앱 스토어 패키지는 Umbrel 팀이 다시 패키징하므로 업스트림보다 몇 시간 또는 며칠 늦을 수 있습니다. 업데이트 후 BTCPay Server 푸터에서 버전을 확인하세요. 여전히 `2.4.2` 미만이라면, 취약한 인스턴스를 계속 실행하지 말고 Umbrel 대시보드에서 **앱을 중지**한 뒤 패키징된 릴리스를 기다리세요.

전용 Umbrel 가이드는 앱 자체를 다룹니다:

https://planb.academy/tutorials/business/point-of-sale/btcpay-server-umbrel-68e1c535-4322-4507-a69c-9dfcbc36dfd1

### Start9 / StartOS

동일한 논리입니다. StartOS 마켓플레이스에서 BTCPay Server를 업데이트한 뒤 푸터에서 버전을 확인하세요. 패키징된 버전이 아직 `2.4.2`가 아니라면, 해당 버전이 될 때까지 서비스를 중지하세요.

### 관리형 및 제3자 호스팅

다른 사람이 인스턴스를 운영한다면(호스팅 제공업체, 협회, 친구의 서버 등) 여전히 확인이 필요합니다. 운영자에게 푸터에 표시되는 버전 문자열을 요청하고, 아래에 설명된 업데이트 후 자격 증명 교체가 수행되었는지 명시적으로 물어보세요. "업데이트했습니다"는 "macaroons를 교체했습니다"와 같은 답변이 아닙니다.

## Step 3 — 업데이트가 실제로 반영되었는지 검증하기

BTCPay Server 인터페이스를 다시 로드하고 푸터의 버전을 읽으세요. `2.4.2` 이상이어야 합니다.

업데이트 명령이 오류 없이 종료되었다는 사실에 의존하지 마세요. 리소스가 제한된 머신에서는 이미지 가져오기가 조용히 실패하고 이전 컨테이너가 계속 실행될 수 있습니다. 매번 버전을 읽으세요.

## Step 4 — 자격 증명 교체하기

이 단계가 "패치됨"을 "안전함"으로 바꿉니다. 수정본이 배포되기 전에 취약점이 악용되고 있었으므로, 인스턴스가 보유했던 모든 비밀 정보를 공격자에게 알려졌을 가능성이 있는 것으로 취급하세요.

### Lightning: LND

macaroons **및** `macaroons.db` 파일을 다시 생성하세요. macaroon 파일만 삭제하는 것으로는 충분하지 않습니다. LND는 `macaroons.db`에 저장된 루트 키에서 macaroons를 파생하므로, 공격자가 오래된 macaroon의 사본을 가지고 있다면 해당 데이터베이스가 다시 생성될 때까지 접근 권한을 유지합니다.

절차는 다음과 같습니다. LND를 중지하고, 네트워크 디렉터리에서 `macaroons.db`와 `*.macaroon` 파일을 제거한 뒤(메인넷의 경우 LND 데이터 디렉터리 내부의 `data/chain/bitcoin/mainnet/`), LND를 다시 시작하고 잠금 해제하면 파일이 다시 생성됩니다. 먼저 디렉터리를 백업하고, 이전 macaroons를 사용하던 모든 애플리케이션 — BTCPay Server 자체, Zeus, Thunderhub, RTL, Alby, 그리고 직접 작성한 모든 스크립트 — 을 다시 페어링하세요.

LND를 인터넷에 노출하고 있다면, 동시에 TLS 인증서와 모든 `lnd.conf` 자격 증명도 검토하세요.

### Lightning: 다른 백엔드

문자열로 노드에 인증하는 모든 항목은 새 문자열을 받아야 합니다:

- **Core Lightning**: 연결에 사용되는 rune 또는 접근 자격 증명을 다시 생성하세요.
- **Phoenixd**: HTTP 비밀번호를 교체하세요.
- **LNbits 및 유사 항목**: 관리자 키와 인보이스 키를 폐기하고 다시 발급하세요.
- **BTCPay Server 스토어 설정에 저장된 원격 노드 연결 문자열**: 새 비밀 정보로 다시 작성하세요.

### BTCPay Server 내부에서 생성된 핫 온체인 지갑

하드웨어 월렛을 연결하거나 키가 서버에 닿지 않은 xpub를 가져오는 대신, BTCPay Server가 온체인 지갑을 생성하도록 했다면 그 시드는 해당 머신에 존재했습니다.

그 시드는 폐기된 것으로 간주하세요:

1. 새 지갑을 생성하세요. 이상적으로는 키가 다시는 서버에 놓이지 않도록 하드웨어 월렛을 사용하세요.
2. 기존 지갑의 자금을 새 지갑으로 스윕하세요.
3. 스토어 설정의 파생 방식을 새 지갑으로 교체하세요.
4. 기존 시드를 절대 재사용하지 마세요.

조회 전용 설정(xpub 또는 하드웨어 월렛)에는 이 조치가 필요하지 않습니다. 개인 키가 서버에 존재한 적이 없기 때문입니다. 이것이 바로 설치 가이드가 조회 전용 설정을 권장하는 이유입니다.

### BTCPay Server 계정 및 API 키

이 작업을 하는 김에 다음도 수행하세요:

- 인스턴스의 모든 사용자 계정 비밀번호를 변경하세요.
- 모든 Greenfield **API 키**를 폐기하고 다시 발급하세요.
- 2.4.2가 2FA 우회를 수정하므로, 2단계 인증을 다시 등록하세요.
- `Admin Dashboard > Server > Users`를 열고 예상치 못한 계정이 없는지 확인하세요.
- 최근 **지급**, **풀 페이먼트**, **환불**을 검토하여 직접 생성하지 않은 항목이 있는지 확인하세요.
- 웹훅과 그 비밀 정보를 검토하세요.

## Step 5 — 다음 보안 릴리스를 위해 계속 정보 얻기

보안 릴리스는 그것을 알게 된 운영자에게만 도움이 됩니다:

- [GitHub의 BTCPay Server 릴리스](https://github.com/btcpayserver/btcpayserver/releases)를 구독하세요 — GitHub는 저장소의 새 릴리스마다 이메일을 보낼 수 있습니다.
- 프로젝트의 공지 채널과 [공식 블로그](https://blog.btcpayserver.org/)를 팔로우하세요.
- 빠르게 업데이트할 수 있는 버전으로 인스턴스를 유지하세요. 뒤처질수록 긴급 업데이트는 더 고통스러워집니다.

자체 호스팅은 결제에 대한 주권을 제공합니다. 그 주권의 비용은 정확히 이것입니다. 릴리스 노트를 읽고 직접 패치하는 사람이 되는 것.
