اجرای پردازشگر پرداخت خودتان یعنی شما تیم امنیتی خودتان نیز هستید. وقتی نگه‌داران BTCPay Server یک انتشار امنیتی منتشر می‌کنند، هیچ‌کس نمونه شما را به‌جای شما وصله نمی‌کند: به‌روزرسانی، راستی‌آزمایی و چرخاندن اعتبارنامه‌هایی که پس از آن می‌آید بر عهده شماست.

این آموزش کل روند را، فارغ از روشی که با آن BTCPay Server را مستقر کرده‌اید، توضیح می‌دهد: نسخه در حال اجرا را بررسی کنید، به‌روزرسانی را برای نوع استقرار خود اعمال کنید، مطمئن شوید که واقعاً اعمال شده است، و رازهایی را که ممکن است مهاجم هنگام آسیب‌پذیر بودن نمونه شما گرفته باشد بچرخانید.

## آسیب‌پذیری حیاتی اوت 2026

⚠️ **هشدار امنیتی حیاتی (7 اوت 2026):** یک آسیب‌پذیری حیاتی که BTCPay Server را تحت تأثیر قرار می‌دهد هم‌اکنون به‌طور فعال مورد سوءاستفاده قرار می‌گیرد و می‌تواند به از دست رفتن وجوه منجر شود. نمونه خود را فوراً از مسیر `Admin Dashboard > Server > Maintenance > Update` به **نسخه 2.4.2** به‌روزرسانی کنید، سپس بررسی کنید که پاورقی `2.4.2` را نمایش دهد. اگر نمی‌توانید بلافاصله به‌روزرسانی کنید، BTCPay Server خود را خاموش کنید. پس از به‌روزرسانی، باید macaroons و `macaroons.db` خود را نیز کاملاً بازسازی کنید، رشته‌های احراز هویت هر بک‌اند Lightning دیگر را کاملاً از نو بسازید، و اگر یک کیف‌پول داغ on-chain داخل BTCPay Server ساخته‌اید، آن وجوه را منتقل کنید و کیف‌پول را از نو بسازید. یکپارچه‌سازان نیز باید NBXplorer را به نسخه 2.6.10 به‌روزرسانی کنند. منبع: [یادداشت‌های انتشار BTCPay Server 2.4.2](https://github.com/btcpayserver/btcpayserver/releases/tag/v2.4.2).

نسخه 2.4.2 در 7 اوت 2026 منتشر شد. یادداشت‌های انتشار می‌گویند که این نسخه یک آسیب‌پذیری حیاتی را برطرف می‌کند که پیش‌تر در دنیای واقعی مورد سوءاستفاده قرار می‌گرفت و توسط `brunoerg` و `benthecarman` از طریق تلاش Bitcoin Red Team گزارش شده بود. همین انتشار همچنین یک دور زدن احراز هویت دومرحله‌ای TOTP از طریق احراز هویت Greenfield Basic را برطرف می‌کند و احراز هویت Greenfield Basic را به‌طور پیش‌فرض 5 دقیقه پس از ایجاد حساب غیرفعال می‌کند.

از «مورد سوءاستفاده فعال» بودن دو پیامد به دست می‌آید:

- **به‌روزرسانی اختیاری نیست و چیزی نیست که برای هفته آینده زمان‌بندی شود.** یک نمونه وصله‌نشده که از اینترنت قابل دسترسی است باید یا به‌روزرسانی شود یا خاموش گردد.
- **به‌روزرسانی به‌تنهایی کافی نیست.** اگر نمونه شما پیش از وصله شدن به خطر افتاده باشد، مهاجم ممکن است از قبل کپی‌هایی از اعتبارنامه‌های Lightning شما و از هر ماده کلید کیف‌پول داغی که BTCPay Server برای شما تولید کرده است در اختیار داشته باشد. این رازها پس از به‌روزرسانی معتبر می‌مانند تا زمانی که آن‌ها را بچرخانید. بخش چرخاندن در پایین همان بخشی است که افراد معمولاً از آن می‌گذرند، و همان بخشی است که واقعاً از وجوه شما محافظت می‌کند.

## مرحله 1 — بفهمید کدام نسخه را اجرا می‌کنید

وارد BTCPay Server خود شوید و به **پاورقی هر صفحه** نگاه کنید: رشته نسخه آنجا نمایش داده می‌شود. همچنین می‌توانید `Admin Dashboard > Server > Maintenance` را باز کنید، که نسخه فعلی و کنترل‌های به‌روزرسانی را نشان می‌دهد.

اگر نمونه شما Greenfield API را در معرض دسترس قرار می‌دهد، `GET /api/v1/server/info` نیز نسخه را برمی‌گرداند.

هر چیزی پایین‌تر از `2.4.2` آسیب‌پذیر است.

## مرحله 2 — به‌روزرسانی

### استقرار Docker خودمیزبان (نصب استاندارد)

این بخش استقرار رسمی Docker را پوشش می‌دهد؛ همان چیزی که از مستندات BTCPay Server، از راه‌انداز یک‌کلیکی LunaNode، و از بیشتر نصب‌های VPS دریافت می‌کنید.

ساده‌ترین مسیر رابط وب است:

1. به `Admin Dashboard > Server > Maintenance` بروید.
2. روی **به‌روزرسانی** کلیک کنید.
3. منتظر بمانید تا کانتینرها دریافت و دوباره راه‌اندازی شوند. رابط برای چند دقیقه در دسترس نخواهد بود.

اگر رابط وب قابل دسترس نیست، یا ترجیح می‌دهید لاگ‌ها را ببینید، این کار را از طریق SSH انجام دهید:

```bash
sudo su -
cd "$BTCPAY_BASE_DIRECTORY/btcpayserver-docker"
. ./btcpay-update.sh
```

در یک نصب پیش‌فرض، `$BTCPAY_BASE_DIRECTORY` برابر `/root` است، پس دایرکتوری `/root/btcpayserver-docker` است. اسکریپت جدیدترین imageها را دریافت می‌کند، کانتینرها را دوباره می‌سازد و نسخه‌های حاصل را چاپ می‌کند.

استقرار Docker، NBXplorer را همراه BTCPay Server ارائه می‌کند، پس یک به‌روزرسانی استاندارد NBXplorer را نیز به `2.6.10` توصیه‌شده می‌رساند. اگر NBXplorer را جداگانه اجرا می‌کنید — چیزی که برای یکپارچه‌سازان و پشته‌های سفارشی معمول است — آن را صریحاً به‌روزرسانی کنید.

### Umbrel

داشبورد Umbrel را باز کنید، به **App Store** بروید، BTCPay Server را پیدا کنید و اگر به‌روزرسانی ارائه شده است آن را اعمال کنید.

⚠️ **مهم:** بسته‌های فروشگاه اپلیکیشن توسط تیم Umbrel دوباره بسته‌بندی می‌شوند و ممکن است ساعت‌ها یا روزها از بالادست عقب بمانند. پس از به‌روزرسانی، نسخه را در پاورقی BTCPay Server بررسی کنید. اگر هنوز پایین‌تر از `2.4.2` است، از داشبورد Umbrel **اپلیکیشن را متوقف کنید** و به‌جای روشن گذاشتن یک نمونه آسیب‌پذیر، منتظر انتشار بسته‌بندی‌شده بمانید.

### Start9 / StartOS

منطق همان است: BTCPay Server را از بازارچه StartOS به‌روزرسانی کنید، سپس نسخه را در پاورقی راستی‌آزمایی کنید. اگر نسخه بسته‌بندی‌شده هنوز `2.4.2` نیست، سرویس را تا زمانی که به آن نسخه برسد متوقف کنید.

### میزبانی مدیریت‌شده و شخص ثالث

اگر شخص دیگری نمونه شما را اداره می‌کند (یک ارائه‌دهنده میزبانی، یک انجمن، سرور یک دوست)، همچنان به تأیید نیاز دارید. از اپراتور رشته نسخه نشان‌داده‌شده در پاورقی را بخواهید، و صریحاً بپرسید آیا چرخاندن اعتبارنامه پس از به‌روزرسانی که در پایین توضیح داده شده انجام شده است یا نه. «به‌روزرسانی کردیم» همان پاسخ «macaroons شما را چرخاندیم» نیست.

## مرحله 3 — راستی‌آزمایی کنید که به‌روزرسانی واقعاً اعمال شده است

رابط BTCPay Server را دوباره بارگذاری کنید و نسخه را در پاورقی بخوانید. باید `2.4.2` یا بالاتر را نشان دهد.

به خروج بدون خطای فرمان به‌روزرسانی تکیه نکنید: روی ماشین‌های محدود، دریافت یک image می‌تواند بی‌صدا شکست بخورد و کانتینر قبلی را در حال اجرا باقی بگذارد. هر بار نسخه را بخوانید.

## مرحله 4 — اعتبارنامه‌های خود را بچرخانید

این همان مرحله‌ای است که «وصله‌شده» را به «امن» تبدیل می‌کند. چون این آسیب‌پذیری پیش از انتشار اصلاحیه مورد سوءاستفاده قرار می‌گرفت، با هر رازی که نمونه شما در اختیار داشت به‌عنوان چیزی رفتار کنید که ممکن است برای مهاجم شناخته شده باشد.

### Lightning: LND

macaroons **و** فایل `macaroons.db` را دوباره تولید کنید. حذف فقط فایل‌های macaroon کافی نیست — LND، macaroons را از کلید ریشه ذخیره‌شده در `macaroons.db` مشتق می‌کند، پس مهاجمی که کپی یک macaroon قدیمی را دارد تا زمانی که آن پایگاه داده دوباره ساخته نشود دسترسی خود را حفظ می‌کند.

روند این است: LND را متوقف کنید، `macaroons.db` و فایل‌های `*.macaroon` را از دایرکتوری شبکه حذف کنید (برای mainnet، مسیر `data/chain/bitcoin/mainnet/` داخل دایرکتوری داده LND)، سپس LND را دوباره راه‌اندازی و قفل‌گشایی کنید تا آن‌ها را دوباره بسازد. ابتدا از دایرکتوری پشتیبان بگیرید، و هر اپلیکیشنی را که از macaroons قدیمی استفاده می‌کرد دوباره جفت کنید — خود BTCPay Server، Zeus، Thunderhub، RTL، Alby، و هر اسکریپتی که نوشته‌اید.

اگر LND را روی اینترنت نیز در معرض دسترس قرار می‌دهید، هم‌زمان گواهی TLS آن و هر اعتبارنامه‌ای در `lnd.conf` را نیز بازبینی کنید.

### Lightning: سایر بک‌اندها

هر چیزی که با یک رشته به نود شما احراز هویت می‌کند باید یک رشته جدید بگیرد:

- **Core Lightning**: rune یا اعتبارنامه‌های دسترسی استفاده‌شده توسط اتصال را دوباره تولید کنید.
- **Phoenixd**: گذرواژه HTTP را بچرخانید.
- **LNbits و مشابه‌ها**: کلیدهای مدیر و فاکتور را لغو و دوباره صادر کنید.
- **رشته‌های اتصال نود راه‌دور** ذخیره‌شده در تنظیمات فروشگاه BTCPay Server: آن‌ها را با رازهای جدید بازنویسی کنید.

### کیف‌پول داغ on-chain تولیدشده داخل BTCPay Server

اگر اجازه داده‌اید BTCPay Server برای شما یک کیف‌پول on-chain تولید کند — برخلاف اتصال یک کیف‌پول سخت‌افزاری یا وارد کردن یک xpub که کلیدهایش هرگز با سرور تماس نداشته‌اند — آن seed روی ماشین زندگی می‌کرده است.

آن را سوخته فرض کنید:

1. یک کیف‌پول جدید بسازید، ترجیحاً با یک کیف‌پول سخت‌افزاری تا کلیدها دیگر هرگز روی سرور قرار نگیرند.
2. وجوه را از کیف‌پول قدیمی به کیف‌پول جدید به‌صورت کامل منتقل کنید.
3. طرح مشتق‌سازی را در تنظیمات فروشگاه با کیف‌پول جدید جایگزین کنید.
4. هرگز seed قدیمی را دوباره استفاده نکنید.

پیکربندی‌های watch-only (xpub یا کیف‌پول سخت‌افزاری) به این کار نیاز ندارند: کلیدهای خصوصی هرگز روی سرور نبوده‌اند. دقیقاً به همین دلیل است که راهنمای نصب آن‌ها را توصیه می‌کند.

### حساب‌های BTCPay Server و کلیدهای API

در همین حین:

- گذرواژه‌های همه حساب‌های کاربری روی نمونه را تغییر دهید.
- همه **کلیدهای API** مربوط به Greenfield را لغو و دوباره صادر کنید.
- احراز هویت دومرحله‌ای را دوباره ثبت‌نام کنید، چون 2.4.2 یک دور زدن 2FA را برطرف می‌کند.
- `Admin Dashboard > Server > Users` را باز کنید و بررسی کنید که هیچ حساب غیرمنتظره‌ای وجود نداشته باشد.
- **پرداخت‌های خروجی**، **pull payments** و **بازپرداخت‌های** اخیر را برای ورودی‌هایی که شما ایجاد نکرده‌اید بازبینی کنید.
- webhooks و رازهای آن‌ها را بازبینی کنید.

## مرحله 5 — برای مورد بعدی مطلع بمانید

انتشارهای امنیتی فقط به اپراتورهایی کمک می‌کنند که درباره آن‌ها می‌شنوند:

- [انتشارهای BTCPay Server در GitHub](https://github.com/btcpayserver/btcpayserver/releases) را دنبال کنید — GitHub می‌تواند برای هر انتشار جدید یک مخزن به شما ایمیل بزند.
- کانال‌های اعلام پروژه و [وبلاگ رسمی](https://blog.btcpayserver.org/) را دنبال کنید.
- نمونه خود را روی نسخه‌ای نگه دارید که بتوانید سریع به‌روزرسانی‌اش کنید: هرچه عقب‌تر باشید، یک به‌روزرسانی اضطراری دردناک‌تر می‌شود.

خودمیزبانی به شما حاکمیت بر پرداخت‌هایتان می‌دهد. هزینه آن حاکمیت دقیقاً همین است: خواندن یادداشت‌های انتشار و کسی بودن که وصله می‌کند.
