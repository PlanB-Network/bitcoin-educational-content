การรันตัวประมวลผลการชำระเงินของคุณเองหมายความว่าคุณก็เป็นทีมรักษาความปลอดภัยของตัวเองด้วยเช่นกัน เมื่อผู้ดูแล BTCPay Server เผยแพร่รุ่นความปลอดภัย จะไม่มีใครแพตช์อินสแตนซ์ของคุณให้คุณ: การอัปเดต การตรวจสอบยืนยัน และการหมุนเวียนข้อมูลประจำตัวหลังจากนั้น ล้วนเป็นสิ่งที่คุณต้องลงมือทำเอง

บทแนะนำนี้จะพาคุณผ่านขั้นตอนทั้งหมด ไม่ว่าคุณจะปรับใช้ BTCPay Server ด้วยวิธีใด: ตรวจสอบเวอร์ชันที่กำลังรัน ใช้อัปเดตตามประเภทการปรับใช้ของคุณ ตรวจสอบยืนยันว่าอัปเดตถูกนำไปใช้จริง และหมุนเวียนความลับที่ผู้โจมตีอาจจับไปได้ในช่วงที่อินสแตนซ์ของคุณยังมีช่องโหว่

หากคุณยังไม่ได้ปรับใช้ BTCPay Server ให้เริ่มจากคู่มือการติดตั้ง:

https://planb.academy/tutorials/business/point-of-sale/btcpay-server-928eb01e-824b-4b57-a3e8-8727633beddc

## ช่องโหว่ขั้นวิกฤตเดือนสิงหาคม 2026

⚠️ **การแจ้งเตือนความปลอดภัยขั้นวิกฤต (7 สิงหาคม 2026):** ขณะนี้มีช่องโหว่ร้ายแรงที่ส่งผลกระทบต่อ BTCPay Server ซึ่งกำลังถูกโจมตีอย่างต่อเนื่องและอาจทำให้สูญเสียเงินทุนได้ กรุณาอัปเดตอินสแตนซ์ของคุณเป็น **version 2.4.2** ทันทีผ่าน `Admin Dashboard > Server > Maintenance > Update` จากนั้นตรวจสอบว่าส่วนท้ายหน้า (footer) แสดงเป็น `2.4.2` หากคุณไม่สามารถอัปเดตได้ในทันที ให้ปิดการทำงานของ BTCPay Server ของคุณ เมื่ออัปเดตเสร็จแล้ว คุณยังต้องสร้าง macaroons และ `macaroons.db` ขึ้นใหม่ทั้งหมด สร้างสตริงการยืนยันตัวตนของ Lightning backend อื่น ๆ ขึ้นใหม่ทั้งหมด และหากคุณสร้างกระเป๋าเงินแบบ hot on-chain ไว้ภายใน BTCPay Server ให้ย้ายเงินออกจากกระเป๋านั้นและสร้างกระเป๋าใหม่ ผู้ที่ทำการเชื่อมต่อระบบ (integrators) ควรอัปเดต NBXplorer เป็น version 2.6.10 ด้วย แหล่งที่มา: [บันทึกประจำรุ่น BTCPay Server 2.4.2](https://github.com/btcpayserver/btcpayserver/releases/tag/v2.4.2)

เวอร์ชัน 2.4.2 เผยแพร่เมื่อวันที่ 7 สิงหาคม 2026 บันทึกประจำรุ่นระบุว่าเวอร์ชันนี้แก้ไขช่องโหว่ขั้นวิกฤตที่ถูกโจมตีจริงอยู่แล้ว ซึ่งรายงานโดย `brunoerg` และ `benthecarman` ผ่านความพยายาม Bitcoin Red Team รุ่นเดียวกันนี้ยังแก้ไขการข้ามการยืนยันตัวตนสองขั้นตอนแบบ TOTP ผ่านการยืนยันตัวตน Greenfield Basic และปิดใช้งานการยืนยันตัวตน Greenfield Basic ตามค่าเริ่มต้นห้านาทีหลังจากสร้างบัญชี

ผลที่ตามมาจากคำว่า "ถูกโจมตีอย่างต่อเนื่อง" มีสองข้อ:

- **การอัปเดตไม่ใช่ทางเลือก และไม่ใช่สิ่งที่ควรนัดไว้ทำสัปดาห์หน้า** อินสแตนซ์ที่ยังไม่ได้แพตช์และเข้าถึงได้จากอินเทอร์เน็ตต้องถูกอัปเดตหรือปิดการทำงาน
- **การอัปเดตเพียงอย่างเดียวไม่เพียงพอ** หากอินสแตนซ์ของคุณถูกเจาะก่อนที่คุณจะแพตช์ ผู้โจมตีอาจมีสำเนาข้อมูลประจำตัว Lightning ของคุณและข้อมูลคีย์ใด ๆ ของ hot wallet ที่ BTCPay Server สร้างให้คุณอยู่แล้ว ความลับเหล่านั้นยังคงใช้ได้หลังการอัปเดตจนกว่าคุณจะหมุนเวียนสิ่งเหล่านั้น ส่วนการหมุนเวียนด้านล่างคือส่วนที่ผู้คนมักข้าม และเป็นส่วนที่ปกป้องเงินทุนของคุณจริง ๆ

## ขั้นตอนที่ 1 — ตรวจสอบว่าคุณกำลังรันเวอร์ชันใด

เข้าสู่ระบบ BTCPay Server ของคุณและดูที่ **ส่วนท้ายของหน้าใดก็ได้**: สตริงเวอร์ชันจะแสดงอยู่ตรงนั้น คุณยังสามารถเปิด `Admin Dashboard > Server > Maintenance` ซึ่งจะแสดงเวอร์ชันปัจจุบันและส่วนควบคุมการอัปเดต

หากอินสแตนซ์ของคุณเปิดเผย Greenfield API, `GET /api/v1/server/info` จะส่งคืนเวอร์ชันเช่นกัน

ทุกเวอร์ชันที่ต่ำกว่า `2.4.2` มีช่องโหว่

## ขั้นตอนที่ 2 — อัปเดต

### การปรับใช้ Docker แบบโฮสต์เอง (การติดตั้งมาตรฐาน)

ส่วนนี้ครอบคลุมการปรับใช้ Docker อย่างเป็นทางการ ซึ่งเป็นสิ่งที่คุณได้รับจากเอกสารของ BTCPay Server จากตัวเปิดแบบคลิกเดียวของ LunaNode และจากการติดตั้งบน VPS ส่วนใหญ่

เส้นทางที่ง่ายที่สุดคืออินเทอร์เฟซเว็บ:

1. ไปที่ `Admin Dashboard > Server > Maintenance`.
2. คลิก **Update**.
3. รอให้คอนเทนเนอร์ถูกดึงและรีสตาร์ต อินเทอร์เฟซจะไม่พร้อมใช้งานเป็นเวลาสองสามนาที

หากอินเทอร์เฟซเว็บเข้าถึงไม่ได้ หรือคุณต้องการดูล็อก ให้ทำผ่าน SSH:

```bash
sudo su -
cd "$BTCPAY_BASE_DIRECTORY/btcpayserver-docker"
. ./btcpay-update.sh
```

ในการติดตั้งค่าเริ่มต้น `$BTCPAY_BASE_DIRECTORY` คือ `/root` ดังนั้นไดเรกทอรีคือ `/root/btcpayserver-docker` สคริปต์จะดึงอิมเมจล่าสุด สร้างคอนเทนเนอร์ใหม่ และพิมพ์เวอร์ชันผลลัพธ์ออกมา

การปรับใช้ Docker จะมาพร้อมกับ NBXplorer เคียงข้าง BTCPay Server ดังนั้นการอัปเดตมาตรฐานจะอัปเดต NBXplorer ไปยัง `2.6.10` ที่แนะนำด้วย หากคุณรัน NBXplorer แยกต่างหาก — ซึ่งพบได้ทั่วไปสำหรับผู้ผสานรวมระบบและสแต็กแบบกำหนดเอง — ให้อัปเดตมันอย่างชัดเจน

### Umbrel

เปิดแดชบอร์ด Umbrel ไปที่ **App Store** ค้นหา BTCPay Server และใช้อัปเดตหากมีให้

⚠️ **สำคัญ:** แพ็กเกจใน app store ถูกแพ็กใหม่โดยทีม Umbrel และอาจตาม upstream ช้ากว่าหลายชั่วโมงหรือหลายวัน ตรวจสอบเวอร์ชันในส่วนท้ายของ BTCPay Server หลังอัปเดต หากยังต่ำกว่า `2.4.2` ให้ **หยุดแอป** จากแดชบอร์ด Umbrel และรอรุ่นที่ถูกแพ็กมาให้ แทนที่จะปล่อยให้อินสแตนซ์ที่มีช่องโหว่ยังคงทำงานอยู่

คู่มือเฉพาะสำหรับ Umbrel ครอบคลุมตัวแอปเอง:

https://planb.academy/tutorials/business/point-of-sale/btcpay-server-umbrel-68e1c535-4322-4507-a69c-9dfcbc36dfd1

### Start9 / StartOS

ตรรกะเดียวกัน: อัปเดต BTCPay Server จากตลาดของ StartOS แล้วตรวจสอบเวอร์ชันในส่วนท้าย หากเวอร์ชันที่ถูกแพ็กยังไม่ใช่ `2.4.2` ให้หยุดบริการจนกว่าจะเป็นเวอร์ชันนั้น

### โฮสติ้งแบบมีผู้จัดการและจากบุคคลที่สาม

หากมีผู้อื่นดำเนินการอินสแตนซ์ของคุณ (ผู้ให้บริการโฮสติ้ง สมาคม เซิร์ฟเวอร์ของเพื่อน) คุณก็ยังต้องได้รับการยืนยัน ขอให้ผู้ดำเนินการแจ้งสตริงเวอร์ชันที่แสดงในส่วนท้าย และถามอย่างชัดเจนว่าการหมุนเวียนข้อมูลประจำตัวหลังอัปเดตที่อธิบายด้านล่างได้ดำเนินการแล้วหรือไม่ "เราอัปเดตแล้ว" ไม่ใช่คำตอบเดียวกับ "เราได้หมุนเวียน macaroons ของคุณแล้ว"

## ขั้นตอนที่ 3 — ตรวจสอบยืนยันว่าอัปเดตถูกนำไปใช้จริง

โหลดอินเทอร์เฟซ BTCPay Server ใหม่และอ่านเวอร์ชันในส่วนท้าย ต้องแสดง `2.4.2` หรือสูงกว่า

อย่าพึ่งพาแค่ว่าคำสั่งอัปเดตจบโดยไม่มีข้อผิดพลาด: บนเครื่องที่มีทรัพยากรจำกัด การดึงอิมเมจอาจล้มเหลวอย่างเงียบ ๆ และปล่อยให้คอนเทนเนอร์ก่อนหน้ายังคงทำงานอยู่ อ่านเวอร์ชันทุกครั้ง

## ขั้นตอนที่ 4 — หมุนเวียนข้อมูลประจำตัวของคุณ

นี่คือขั้นตอนที่เปลี่ยนจาก "แพตช์แล้ว" เป็น "ปลอดภัย" เนื่องจากช่องโหว่ถูกโจมตีก่อนที่แพตช์จะถูกปล่อยออกมา ให้ถือว่าความลับทุกอย่างที่อินสแตนซ์ของคุณถืออยู่เป็นสิ่งที่ผู้โจมตีอาจรู้แล้ว

### Lightning: LND

สร้าง macaroons **และ**ไฟล์ `macaroons.db` ใหม่ การลบไฟล์ macaroon เพียงอย่างเดียวไม่เพียงพอ — LND สร้าง macaroons จาก root key ที่เก็บไว้ใน `macaroons.db` ดังนั้นผู้โจมตีที่ถือสำเนาของ macaroon เก่าไว้จะยังคงเข้าถึงได้จนกว่าฐานข้อมูลนั้นจะถูกสร้างใหม่

ขั้นตอนคือ: หยุด LND, ลบ `macaroons.db` และไฟล์ `*.macaroon` ออกจากไดเรกทอรีเครือข่าย (สำหรับ mainnet คือ `data/chain/bitcoin/mainnet/` ภายในไดเรกทอรีข้อมูลของ LND) จากนั้นรีสตาร์ตและปลดล็อก LND ซึ่งจะสร้างไฟล์เหล่านี้ขึ้นใหม่ สำรองไดเรกทอรีก่อน และจับคู่แอปพลิเคชันทุกตัวที่ใช้ macaroons เก่าใหม่อีกครั้ง — ตัว BTCPay Server เอง, Zeus, Thunderhub, RTL, Alby และสคริปต์ใด ๆ ที่คุณเขียนไว้

หากคุณเปิดเผย LND ผ่านอินเทอร์เน็ตด้วย ให้ตรวจสอบใบรับรอง TLS และข้อมูลประจำตัวใด ๆ ใน `lnd.conf` พร้อมกัน

### Lightning: backend อื่น ๆ

ทุกสิ่งที่ยืนยันตัวตนกับโหนดของคุณด้วยสตริงต้องได้รับสตริงใหม่:

- **Core Lightning**: สร้าง rune หรือข้อมูลประจำตัวการเข้าถึงที่การเชื่อมต่อใช้อยู่ใหม่
- **Phoenixd**: หมุนเวียนรหัสผ่าน HTTP
- **LNbits และระบบที่คล้ายกัน**: เพิกถอนและออกคีย์ admin และ invoice ใหม่
- **สตริงการเชื่อมต่อ remote node** ที่เก็บไว้ในการตั้งค่าร้านค้าของ BTCPay Server: เขียนใหม่ด้วยความลับชุดใหม่

### Hot on-chain wallet ที่สร้างไว้ภายใน BTCPay Server

หากคุณให้ BTCPay Server สร้าง on-chain wallet ให้คุณ — แทนที่จะเชื่อมต่อ hardware wallet หรือนำเข้า xpub ที่คีย์ไม่เคยแตะเซิร์ฟเวอร์ — seed นั้นเคยอยู่บนเครื่องแล้ว

ให้ถือว่ามันถูกเผาไปแล้ว:

1. สร้าง wallet ใหม่ โดยเหมาะที่สุดคือใช้ hardware wallet เพื่อไม่ให้คีย์อยู่บนเซิร์ฟเวอร์อีก
2. Sweep เงินจาก wallet เก่าไปยัง wallet ใหม่
3. แทนที่ derivation scheme ในการตั้งค่าร้านค้าด้วย wallet ใหม่
4. อย่าใช้ seed เก่าอีก

การตั้งค่าแบบ watch-only (xpub หรือ hardware wallet) ไม่จำเป็นต้องทำขั้นตอนนี้: private keys ไม่เคยอยู่บนเซิร์ฟเวอร์ นี่คือเหตุผลพอดีที่คู่มือการติดตั้งแนะนำวิธีเหล่านี้

### บัญชี BTCPay Server และ API keys

ขณะที่คุณกำลังทำอยู่:

- เปลี่ยนรหัสผ่านของบัญชีผู้ใช้ทุกบัญชีบนอินสแตนซ์
- เพิกถอนและออก Greenfield **API keys** ทั้งหมดใหม่
- ลงทะเบียนการยืนยันตัวตนสองขั้นตอนใหม่ เนื่องจาก 2.4.2 แก้ไขการข้าม 2FA
- เปิด `Admin Dashboard > Server > Users` และตรวจสอบว่าไม่มีบัญชีที่ไม่คาดคิดอยู่
- ตรวจสอบ **payouts**, **pull payments** และ **refunds** ล่าสุดว่ามีรายการที่คุณไม่ได้สร้างหรือไม่
- ตรวจสอบ webhooks และความลับของมัน

## ขั้นตอนที่ 5 — รับข่าวสารไว้สำหรับครั้งถัดไป

รุ่นความปลอดภัยช่วยได้เฉพาะผู้ปฏิบัติการที่ได้ยินข่าวเท่านั้น:

- ติดตาม [BTCPay Server releases on GitHub](https://github.com/btcpayserver/btcpayserver/releases) — GitHub สามารถส่งอีเมลถึงคุณได้เมื่อมีรุ่นใหม่ของ repository ทุกครั้ง

- ให้อินสแตนซ์ของคุณอยู่ในเวอร์ชันที่คุณสามารถอัปเดตได้อย่างรวดเร็ว: ยิ่งคุณตามหลังมากเท่าไร การอัปเดตฉุกเฉินก็ยิ่งเจ็บปวดมากขึ้นเท่านั้น
