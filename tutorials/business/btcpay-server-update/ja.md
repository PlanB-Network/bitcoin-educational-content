自分自身の決済プロセッサを運用するということは、自分自身がセキュリティチームにもなるということです。BTCPay Server のメンテナーがセキュリティリリースを公開しても、誰もあなたの代わりにインスタンスへパッチを当ててはくれません。更新、その検証、そしてその後に続く認証情報のローテーションは、あなた自身が行うべき作業です。

このチュートリアルでは、BTCPay Server をどの方法でデプロイした場合でも、手順全体を説明します。実行中のバージョンを確認し、デプロイ方式に応じて更新を適用し、それが実際に反映されたことを検証し、インスタンスが脆弱だった間に攻撃者が取得した可能性のあるシークレットをローテーションします。

まだ BTCPay Server をデプロイしていない場合は、インストールガイドから始めてください：

https://planb.academy/tutorials/business/point-of-sale/btcpay-server-928eb01e-824b-4b57-a3e8-8727633beddc

## 2026年8月の重大な脆弱性

⚠️ **重大なセキュリティ警告（2026年8月7日）:** BTCPay Server に影響する重大な脆弱性が実際に悪用されており、資金の喪失につながるおそれがあります。直ちに `Admin Dashboard > Server > Maintenance > Update` から **バージョン 2.4.2** へ更新し、フッターに `2.4.2` と表示されていることを確認してください。すぐに更新できない場合は、BTCPay Server を停止してください。更新後は、macaroons および `macaroons.db` を完全に再生成し、その他の Lightning バックエンドの認証文字列もすべて完全に再生成する必要があります。また、BTCPay Server 内でホットな on-chain ウォレットを生成していた場合は、その資金を移動したうえでウォレットを作成し直してください。インテグレーターの方は NBXplorer もバージョン 2.6.10 へ更新してください。出典: [BTCPay Server 2.4.2 リリースノート](https://github.com/btcpayserver/btcpayserver/releases/tag/v2.4.2)。

バージョン 2.4.2 は 2026年8月7日に公開されました。リリースノートによると、このリリースでは、Bitcoin Red Team の取り組みを通じて `brunoerg` と `benthecarman` によって報告された、すでに実際に悪用されていた重大な脆弱性が修正されています。同じリリースでは、Greenfield Basic 認証を通じた TOTP 二要素認証のバイパスも修正され、アカウント作成から5分後に Greenfield Basic 認証がデフォルトで無効化されます。

「実際に悪用されている」ことから、2つの結果が生じます：

- **更新は任意ではなく、来週に予定しておけばよいものでもありません。** インターネットから到達可能な未パッチのインスタンスは、更新するか停止するかのどちらかが必要です。
- **更新だけでは十分ではありません。** パッチ適用前にインスタンスが侵害されていた場合、攻撃者はすでにあなたの Lightning 認証情報や、BTCPay Server が生成したホットウォレットの鍵素材のコピーを保持している可能性があります。それらのシークレットは、あなたがローテーションするまで、更新後も有効なままです。以下のローテーションセクションは、多くの人が省略してしまう部分であり、実際にあなたの資金を守る部分です。

## ステップ 1 — 実行中のバージョンを確認する

BTCPay Server にログインし、**任意のページのフッター**を確認してください。そこにバージョン文字列が表示されています。`Admin Dashboard > Server > Maintenance` を開くこともでき、そこには現在のバージョンと更新コントロールが表示されます。

インスタンスが Greenfield API を公開している場合、`GET /api/v1/server/info` でもバージョンが返されます。

`2.4.2` 未満はすべて脆弱です。

## ステップ 2 — 更新する

### セルフホスト Docker デプロイ（標準インストール）

これは、BTCPay Server のドキュメント、LunaNode のワンクリックランチャー、そして大半の VPS インストールで利用される、公式 Docker デプロイを対象としています。

最も簡単な方法は Web インターフェースです：

1. `Admin Dashboard > Server > Maintenance` に移動します。
2. **Update** をクリックします。
3. コンテナが取得され、再起動されるまで待ちます。インターフェースは数分間利用できなくなります。

Web インターフェースに到達できない場合、またはログを確認したい場合は、SSH 経由で実行します：

```bash
sudo su -
cd "$BTCPAY_BASE_DIRECTORY/btcpayserver-docker"
. ./btcpay-update.sh
```

デフォルトのインストールでは `$BTCPAY_BASE_DIRECTORY` は `/root` なので、ディレクトリは `/root/btcpayserver-docker` です。このスクリプトは最新のイメージを取得し、コンテナを再作成し、結果として得られたバージョンを出力します。

Docker デプロイでは BTCPay Server と一緒に NBXplorer も同梱されているため、標準的な更新では NBXplorer も推奨される `2.6.10` になります。インテグレーターやカスタムスタックで典型的なように、NBXplorer を別途実行している場合は、明示的に更新してください。

### Umbrel

Umbrel ダッシュボードを開き、**App Store** に移動し、BTCPay Server を見つけ、更新が提供されている場合は適用します。

⚠️ **重要:** app-store パッケージは Umbrel チームによって再パッケージ化されるため、上流版から数時間または数日遅れることがあります。更新後、BTCPay Server のフッターでバージョンを確認してください。まだ `2.4.2` 未満である場合は、脆弱なインスタンスを実行したままにするのではなく、Umbrel ダッシュボードから **アプリを停止** し、パッケージ化されたリリースを待ってください。

専用の Umbrel ガイドでは、アプリ自体を扱っています：

https://planb.academy/tutorials/business/point-of-sale/btcpay-server-umbrel-68e1c535-4322-4507-a69c-9dfcbc36dfd1

### Start9 / StartOS

同じ考え方です。StartOS マーケットプレイスから BTCPay Server を更新し、その後フッターでバージョンを確認します。パッケージ版がまだ `2.4.2` でない場合は、そうなるまでサービスを停止してください。

### マネージドおよびサードパーティのホスティング

誰か他の人があなたのインスタンスを運用している場合（ホスティングプロバイダー、団体、友人のサーバーなど）でも、確認は必要です。運用者にフッターに表示されるバージョン文字列を尋ね、以下で説明する更新後の認証情報ローテーションが実施済みかどうかを明示的に尋ねてください。「更新しました」は「macaroons をローテーションしました」と同じ回答ではありません。

## ステップ 3 — 更新が実際に反映されたことを検証する

BTCPay Server インターフェースを再読み込みし、フッターのバージョンを確認してください。`2.4.2` 以上でなければなりません。

更新コマンドがエラーなしで終了したことに依存しないでください。リソースの限られたマシンでは、イメージの取得が静かに失敗し、以前のコンテナが実行されたままになることがあります。毎回、バージョンを確認してください。

## ステップ 4 — 認証情報をローテーションする

これは「パッチ済み」を「安全」に変えるステップです。修正が配布される前に脆弱性が悪用されていたため、インスタンスが保持していたすべてのシークレットは攻撃者に知られている可能性があるものとして扱ってください。

### Lightning: LND

macaroons **および** `macaroons.db` ファイルを再生成してください。macaroon ファイルだけを削除しても十分ではありません。LND は `macaroons.db` に保存されたルートキーから macaroons を導出するため、古い macaroon のコピーを保持している攻撃者は、そのデータベースが再作成されるまでアクセスを維持できます。

手順は次のとおりです。LND を停止し、LND データディレクトリ内のネットワークディレクトリ（mainnet の場合は `data/chain/bitcoin/mainnet/`）から `macaroons.db` と `*.macaroon` ファイルを削除し、その後 LND を再起動してアンロックします。これにより、それらが再作成されます。まずディレクトリをバックアップし、古い macaroons を使用していたすべてのアプリケーションを再ペアリングしてください。BTCPay Server 自体、Zeus、Thunderhub、RTL、Alby、そしてあなたが書いたすべてのスクリプトが対象です。

LND もインターネットに公開している場合は、同時に TLS 証明書と `lnd.conf` の認証情報も確認してください。

### Lightning: その他のバックエンド

文字列であなたのノードに認証するものはすべて、新しい文字列を取得する必要があります：

- **Core Lightning**: 接続で使用される rune またはアクセス認証情報を再生成します。
- **Phoenixd**: HTTP パスワードをローテーションします。
- **LNbits など**: admin キーと invoice キーを失効させ、再発行します。
- **BTCPay Server のストア設定に保存されたリモートノード接続文字列**: 新しいシークレットで書き直します。

### BTCPay Server 内で生成されたホット on-chain ウォレット

ハードウェアウォレットを接続したり、鍵がサーバーに触れたことのない xpub をインポートしたりするのではなく、BTCPay Server に on-chain ウォレットを生成させた場合、その seed はそのマシン上に存在していました。

それは漏えい済みだと考えてください：

1. 新しいウォレットを作成します。理想的には、鍵が二度とサーバー上に置かれないよう、ハードウェアウォレットを使います。
2. 古いウォレットから新しいウォレットへ資金をスイープします。
3. ストア設定の導出スキームを新しいウォレットに置き換えます。
4. 古い seed は決して再利用しないでください。

ウォッチオンリー構成（xpub またはハードウェアウォレット）では、これは不要です。秘密鍵は一度もサーバー上に存在していません。インストールガイドがそれらを推奨する理由はまさにここにあります。

### BTCPay Server アカウントと API キー

そのついでに：

- インスタンス上のすべてのユーザーアカウントのパスワードを変更します。
- すべての Greenfield **API キー** を失効させ、再発行します。
- 2.4.2 で 2FA バイパスが修正されていることを踏まえ、二要素認証を再登録します。
- `Admin Dashboard > Server > Users` を開き、予期しないアカウントが存在しないことを確認します。
- 最近の **支払い**、**プルペイメント**、**返金** を確認し、あなたが作成していない項目がないか確認します。
- Webhook とそのシークレットを確認します。

## ステップ 5 — 次に備えて情報を得続ける

セキュリティリリースは、それを知った運用者にしか役立ちません：

- [GitHub の BTCPay Server リリース](https://github.com/btcpayserver/btcpayserver/releases) をウォッチしてください。GitHub はリポジトリの新しいリリースごとにメールを送信できます。
- プロジェクトの告知チャンネルと [公式ブログ](https://blog.btcpayserver.org/) をフォローしてください。
- インスタンスは、すばやく更新できるバージョンに保ってください。遅れれば遅れるほど、緊急更新は苦痛になります。

セルフホスティングは、あなたの決済に対する主権を与えます。その主権の代償はまさにこれです。リリースノートを読み、自分でパッチを当てる人になることです。
